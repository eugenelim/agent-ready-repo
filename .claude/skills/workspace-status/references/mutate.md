# Mutate — repair

Load this when the chosen mode is `mutate`. Every subcommand below either
writes a file or exists to prepare a write, so read this page before invoking
any of them.

The authority rule that governs both: you apply only a plan the user has seen
and confirmed. You never confirm on their behalf.

## Repair subcommands

**`repair-plan`** — runs a full reconciliation scan (Type 1+2+3) and builds a deterministic repair plan for all automatically-resolvable Type 2 queue findings: queue entries whose spec shows `Shipped` (moved to `[work].shipped`) or `Archived` (removed from `[work].queue`). Emits a JSON plan to stdout and writes it to `.workspace-repair-plan.json` (override with `--plan-file`). The plan includes a SHA-256 fingerprint of `workspace.toml` so that `repair-apply` can detect stale plans. Type 1 and Type 3 findings, and any Type 2 `active`-list entries, appear in `manual_findings` — they require human review. `Approved` entries are never touched automatically. Exit 0 on success (including empty plan); exit 1 if workspace.toml is absent; exit 2 if the plan file cannot be written (stdout is still emitted).

**`repair-apply`** — loads the plan file written by `repair-plan` (default `.workspace-repair-plan.json`; override with `--plan-file`), verifies the SHA-256 fingerprint against the current `workspace.toml`, and applies each operation atomically via `tempfile.mkstemp`. Re-reads each spec's `Status` from disk at apply time; skips the operation (with a `skipped` record in `per_operation`) if the status has changed since the plan was made. Immediately before replacing `workspace.toml`, it revalidates every spec whose operation would be applied and aborts the whole write if any status or status-line fingerprint changed. Requires `tomlkit` to preserve TOML comments; exits 2 if `tomlkit` is unavailable. The write is skipped entirely when `operations_applied == 0` (no stray temp files). Exit 0 on success or all-skipped; exit 2 for any structural error (fingerprint mismatch, plan not found, parse error, invalid schema).

**`needs-to-header` and `needs-drop-cooled` operations** — a registry entry that still carries typed `needs` is not ready to dispatch, and `repair-plan` moves its edges to the waiting item. For each non-cooled canonical membership with a non-empty typed `needs` array, the plan holds one `needs-to-header` operation: `waiting_path`, `waiting_sha256`, the `registry_edges`, the `depends_on_items` (a typed reference — `spec:<dir>`, `brief:<slug>`, or `<intent kind>:<slug>` — for a spec, brief, or intent target, and the target's path for a captured item), and the `receipt_items` (one `<reference> completion …` or `<reference> coordination …` receipt per edge that carries one). A cooled membership gets a `needs-drop-cooled` operation instead: `waiting_path` and `dropped_cooled`, with no read of the waiting item, because a cooled item contributes no edge. An edge the header cannot hold as the same edge becomes a manual finding naming the waiting path and the target, and its membership gets no operation: a brief or intent target that is missing, retired, or has no `Slug:`; a captured item that carries a completion receipt; a registry `kind` that differs from the target's own kind; a cross-repo edge whose `path` differs from its `containing_brief`; a receipt value outside the receipt grammar; a path holding a comma, a space, or a control character; and a waiting item that is unreadable, a link, multiply linked, or has no `- **Field:**` line to anchor on. When the workspace itself is invalid (`invalid_workspace` or `configuration_mismatch`), the plan holds no operation of any type and no such finding. The plan file holds every path, item, and receipt whole. The plan and `repair-apply` output show each part of an echoed value only when it is a valid reference, path, or receipt token of at most 200 characters with no control character, and show a part that fails as an empty string.

On `repair-apply --yes`, each `needs-to-header` operation is checked under the writer lock: the waiting path must be the `path` of exactly one non-cooled canonical membership, the plan's items must equal the items re-derived from that entry's current `needs`, the waiting file's SHA-256 must match the plan, and the file must be a regular, singly linked file inside the repository with no link in any segment. A failed check refuses that operation and leaves its `needs` as it was. Otherwise the operation adds its items after the last `- **Field:**` line of the preamble, appending to an existing `Depends on:` or `Dependency receipts:` line and skipping an item or a receipt already present for the same reference, and replaces the file atomically. One atomic `workspace.toml` write then sets `needs = []` on the entries that applied and changes no other byte. A `needs-drop-cooled` operation is refused, keeping `needs`, when its membership is no longer cooled or the cooled state cannot be read. An interrupted run leaves `needs` in place, so `unmigrated_needs` keeps refusing the entry, and a rerun of `repair-plan` and `repair-apply` adds nothing twice and clears `needs`.

The output of `repair-apply` compares edges, where an edge is a waiting path, a reference, and a receipt: `header_edges_before` (read from each waiting item before the write; every item counts), `registry_edges` (the registry's edges, without the dropped ones), `dropped_cooled`, and `header_edges_after` (read back from each waiting item; only items the reader accepts count), with `edges_equal` true when the read-back set equals `header_edges_before` plus `registry_edges`. It exits 1 when they differ, and an operation whose edges differ keeps its `needs`.

**`captured-to-file` operation** — a captured item registered outside `docs/product/captured/` is not a captured-item file, and `repair-plan` writes one record for it under `docs/product/captured/`. The command pair is `repair-plan`, then `repair-apply --yes` on the plan file. Show the owner the whole plan file and apply nothing until the owner confirms that exact file: it holds every record slug, kind, and the full record text. Each operation carries `record_path`, `record_text`, and the `entry_locator`; a membership also carries its `source_path`, `source_sha256`, and `registry_fingerprint`, and a legacy captured entry (a slug-only entry) carries its `slug`. A record holds the title, `Status:`, `Kind:`, `Type:` (a legacy entry whose type is a shaping type), `Resolution:` (a closed defect), `Parent intent:`, `Detail:` naming the old note, and then the summary under `## Summary`. The old note's `Depends on:` and `Dependency receipts:` lines are copied into the record, not moved, because the repair never writes a source file; after the repair the old note's copies are inert and may be deleted by hand.

On `repair-apply --yes`, under the shared writer lock, each operation re-derives its content from the current tree and is refused when the plan no longer matches: a changed source file, a changed registry, an edited operation, a membership cooled after planning, a record path now holding other bytes, a record directory that is a link, or cooling state that cannot be read. A refused operation leaves its entry where it was. Records are created exclusively at their final path, then one atomic `workspace.toml` write re-points the applied memberships' `path` and changes no other byte. A record cut short by a crash is a regular file with other bytes; the next `repair-plan` reports it as a manual finding naming its path, the owner removes it, and the next run finishes. The repair never deletes a file. `repair-apply` compares the items before and after: `captured_before` (each item's slug, kind, and source path), `captured_after` (each record read back), the copied dependency lines as `header_edges_before` and `header_edges_after`, and `captured_equal`. It exits 1 when `captured_equal` is false, for example after a record is edited by hand between the write and the read-back. Manual findings in the plan name the item and the reason, such as a status that conflicts with its collection, a typed `needs` still on the entry, an item that is a dependency target, a slug that is invalid or collides, or a record that differs from the one derived.

**`intent-brief-drop` operation** — an intent or brief needs no registry entry, so `repair-plan` holds one `intent-brief-drop` operation for each canonical repo-origin entry that is an intent with a `path` under `docs/product/intents/` or a brief with a `path` under `docs/product/briefs/`, cooled or not. A captured item's entry is never dropped, whatever its `kind`, including one the same run's `captured-to-file` operation moves. Each carries an `entry_locator` (the initiative key, empty for a top-level collection; the collection label such as `brief_queue.executing`; and the index in that collection), the entry's `path` and `kind`, and its `registry_fingerprint`. A tracker-origin entry, an entry of any other kind or location, and a legacy entry get none. `repair-apply --yes` runs every `needs-to-header` and `needs-drop-cooled` operation first. Before it changes anything, it checks each drop against the `workspace.toml` it read under the writer lock: the entry at that initiative, collection, and index must have the planned `path` and `kind`, match the planned fingerprint, and still qualify by that rule at its planned path; the check then holds that entry. After the other operations run, it removes each held entry in the same atomic, comment-preserving `workspace.toml` write, so an array a queue operation shortened cannot redirect a drop. A drop is refused, and its entry kept, when that check fails or when the entry still has `needs` after the needs operations ran, as it does when its `needs-to-header` operation was refused. A run where every needs operation applies leaves no repo-origin intent or brief entry, and the next `repair-plan` holds no `intent-brief-drop` operation. If an intent rename is pending (an `.intent-rename-*` stage exists), tell the user to recover or roll back that rename before `repair-apply`, so the drop reads the registry the rename left.

**`spec-entry-drop` operation** — a spec is registered by its own header, so `repair-plan` holds one `spec-entry-drop` operation for each repo-origin spec entry in a `work.` or `backlog.` collection whose `needs` is empty, or that a `needs-to-header` or `needs-drop-cooled` operation of the same plan empties. Each carries the same `entry_locator`, `path`, `kind`, and `registry_fingerprint` as an `intent-brief-drop` operation. An entry in any other collection, a tracker-origin spec, an entry of another kind, a legacy entry, and a table with no `needs` key get none and keep the finding they have today. A candidate gets no `queue-to-shipped` or `queue-remove` operation: the drop removes it in the same run.

*Held entry.* A cooled candidate is held when its `source.parent` key is present and declares a parent, but its lifecycle record carries no `parent`. The declared parent is `none` when the value is `none`; otherwise it is the value as the provenance normalizer resolves it (a `brief:<slug>` pointer becomes a path), when that path is a brief file listed in `docs/product/briefs/` and matches `docs/product/briefs/<slug>.md` with a lowercase alphanumeric slug of at most 128 characters. An absent key, or any other value, declares no parent, so the entry is dropped and the record is left as it is. A held entry gets no `spec-entry-drop` operation and keeps its collection. The plan holds one manual item for it (`finding_type` 6, reason `held-record-lacks-parent`) naming the entry `path`, the lifecycle record's path (`record_path`), and the `parent` value to add to that record. `workspace-status` never writes a lifecycle record: a person adds the `parent` to the record, and the next `repair-plan` drops the entry. When cooling state cannot be read, the plan holds no `spec-entry-drop` operation and no manual item, and a candidate in `work.queue` still gets no `queue-to-shipped` or `queue-remove` operation; `repair-apply` refuses a planned drop with `cooling_state_unavailable` and keeps the entry.

**`tracker-entry-drop` operation** — a tracker-origin artifact gets no entry: its `source-authority` record carries the tracker profile in a `tracker_profile` table (`id` and `version`), and refresh reads the profile there. `repair-plan` holds one `tracker-entry-drop` operation for each tracker-origin entry, whatever its collection, that matches its artifact: the entry has a `path` to a readable artifact whose one `source-authority` record has the same `source_ref`, the entry's profile is valid and equals the record's table when the record has one, the entry has no `needs`, no other write of the same plan touches the artifact or its path, and no entry finding names it. Each carries the same `entry_locator`, `path`, `kind`, and `registry_fingerprint` as a `spec-entry-drop` operation, plus the artifact's `artifact_sha256` and the `profile` to add (empty when the record already holds an equal table, so the operation only removes the entry). A matched candidate gets no `queue-to-shipped` or `queue-remove` operation. An entry that does not match becomes one manual item (`finding_type` 7) naming the entry and the reason, such as `path-missing`, `artifact-missing`, `record-missing-or-invalid`, `ref-mismatch`, `entry-profile-invalid`, `profile-mismatch`, `needs-present`, `other-write-pending`, `entry-finding`, or `cooling-state-unavailable`, and keeps its entry. The last applies to a tracker-origin spec in a `work.` collection when cooling state cannot be read, because a held entry cannot then be told from a cooled one. A cooled tracker-origin spec whose `source.parent` declares a parent its lifecycle record lacks is held the same way as a spec entry: one manual item (`finding_type` 6, reason `held-record-lacks-parent`), no operation. `workspace-status` never writes a lifecycle record.

`repair-apply --yes` re-derives each drop under the writer lock and refuses it, keeping the entry, when the plan no longer matches. It writes the artifact first, through the confined atomic file write the `needs-to-header` step uses, inserting the table by re-rendering the parsed record and re-parsing the result, then removes the entries in the one `workspace.toml` write. If the `workspace.toml` write fails, the artifact keeps the added table; the next plan treats that entry as matched and the next apply only removes it.

**`captured-entry-drop` operation** — a captured item is registered by its own file, `docs/product/captured/<slug>.md`, so its registry entry is redundant. `repair-plan` holds one `captured-entry-drop` operation for each captured membership whose file is a readable captured file, and for each slug-only legacy entry whose `docs/product/captured/<slug>.md` is readable. An entry that a `captured-to-file` operation of the same plan backs gets its drop in that plan: the operation carries the record bytes the `captured-to-file` write produces and is checked against them after that write. Each operation holds the entry's `entry_locator` and `registry_fingerprint`, the captured file's `file_path` and `file_sha256`, and the entry's `path` or `slug`. Every other such entry becomes one manual item (`finding_type` 8) naming the entry and the reason, `path-invalid`, `path-missing`, `file-cooled`, `record-invalid`, `file-unreadable`, `file-linked`, or `slug-invalid`, and keeps its entry. A `captured-entry-drop` operation never writes a captured file; the same repair's `captured-to-file` operation and the legacy-needs `needs-to-header` step below do write captured files. A captured membership with non-empty `needs` gets a drop only when a `needs-to-header` or `needs-drop-cooled` operation of the same plan covers it; otherwise it keeps its entry and its one manual item.

A slug-only entry with non-empty `needs` (a string or an array of strings) keeps those needs in its captured file first. Each need must be a legacy need: `work:spec/<s>` or `ini-<NNN>:work:spec/<s>` (typed reference `spec:<s>`), `brief:docs/product/briefs/<s>.md` (typed reference `brief:<b>`, where `<b>` is the one slug the dependency resolution index holds for that path), or `backlog:<s>` (reference `docs/product/captured/<s>.md`), with `<s>` a lowercase slug. When every need is a legacy need with a typed reference and the file, judged as it stands after the same plan's `captured-to-file` write, can take them, the plan holds one `needs-to-header` operation for the entry before its drop. It carries the file as `waiting_path`, the `waiting_sha256` of the bytes the drop expects, the `depends_on_items`, and the entry's `entry_locator`, `registry_fingerprint`, and `slug`, and the entry's drop exists only with it. Otherwise the entry becomes one manual item (`finding_type` 8) with the reason `need-not-legacy` (a need of another form), `need-no-typed-reference` (a brief with no single indexed slug), or `header-not-writable` (a file that is not UTF-8, or whose header has a wrapped line), and keeps its entry and its `needs`; that item is the only one the entry gets. On `repair-apply --yes` the operation runs after the file's `captured-to-file` write and after both drop checks, so the drop compares the file and entry as they stood before the header write. It runs only when its drop is held, re-derives the items from the entry's current `needs`, requires the file's SHA-256 to match, adds each typed reference the header does not already hold after the last `- **Field:**` line through the same confined atomic write as `needs-to-header` above, and sets the entry's `needs` to `[]`, so the one `workspace.toml` write removes the entry. One apply settles the entry, and the next `repair-plan` holds neither operation for it.

`repair-apply --yes` re-derives each drop under the writer lock after the `captured-to-file` writes, and refuses it, keeping the entry, when the entry or the file no longer matches the plan. It removes the entries in the one `workspace.toml` write.

**`refresh-policy-move` operation** — refresh reads its role policy from `.work-intake.toml` at the repository root, not from `workspace.toml`. When `workspace.toml` has an `[authorization.refresh]` table that refresh accepts, `repair-plan` holds one `refresh-policy-move` operation. With no policy file its action is `create-and-remove`: it creates `.work-intake.toml` holding that table and removes the table. With a policy file whose parsed table equals the table, its action is `remove`: it only removes the table. Anything else becomes one manual item (`finding_type` 9) with the reason `table-not-accepted`, `refresh-module-unavailable` (the sibling refresh module that defines what refresh accepts could not be loaded), `policy-file-unreadable`, `policy-file-invalid`, or `policy-file-differs`, and nothing moves; the repair never overwrites an existing `.work-intake.toml`.

`repair-apply --yes` re-derives the move under the writer lock and refuses it with `policy_move_mismatch` when the plan no longer matches. It writes the policy file first, through a confined exclusive file write (refusals `policy_path_unsafe`, `policy_file_exists`, `policy_write_failed`, `policy_read_back_failed`), then removes the table in the one `workspace.toml` write. If that write fails, the next plan sees an equal policy file and only removes the table. `[authorization.migration]` stays in `workspace.toml`.

On `repair-apply --yes`, every `needs-to-header` and `needs-drop-cooled` operation runs first, then the queue operations, then the drops, all in one atomic, comment-preserving `workspace.toml` write. Under the writer lock, each drop is re-derived from the registry read there by the rule the plan used: the entry at the planned locator must still be a candidate with the planned `path`, `kind`, and fingerprint, and must not be held, with its record read again. A drop is refused, and its entry kept, when that check fails or when the entry still has `needs` after the needs operations ran. A run where every planned operation applies leaves no candidate except held entries, and the next `repair-plan` holds no `spec-entry-drop` operation.

#### 1e. Repair workflow

Use `repair-plan` + `repair-apply` to deterministically clean up stale queue entries without manual `workspace.toml` editing:

```
# Step 1 — inspect the plan (no writes to workspace.toml)
["<python>", "<skill-dir>/scripts/workspace_status.py", "repair-plan", "--root", "<repo-root>"]

# Step 2 — review the plan JSON; then apply (--yes is required to confirm the write)
["<python>", "<skill-dir>/scripts/workspace_status.py", "repair-apply", "--root", "<repo-root>", "--yes"]
```

**When to use:** when `workspace.toml` still holds entries (dispatch refuses with `unmigrated_workspace`) or stale queue entries, and you want automated cleanup without manual editing. The two-step design lets you review the plan before committing.

**`--plan-file <path>`** — override the plan file location for both subcommands. The path must resolve inside `<repo-root>`; symlinks that escape the root are rejected (exit 2, `plan_file_outside_root`).

**`tomlkit` availability** — `repair-apply` requires `tomlkit` (comment-preserving TOML writer). If absent, `repair-apply` exits 2 with `reason: "tomlkit_unavailable"`; surface to the user and install only with consent: `pip install tomlkit==0.15.1`. See `## Prerequisites` above. `repair-plan` does not require it.

**`repair-apply` result JSON key fields:**

```
schema_version     — 1
mode               — "repair-apply"
applied            — true if write succeeded; false on any structural error
operations_applied — count of operations actually written (0 when all skipped or empty plan)
per_operation      — list of {path, applied, reason?} for all operations
reason             — error reason string when applied:false (top-level field, structural errors)
```

**Interpreting `per_operation`:** each entry records `"applied": true` (written) or `"applied": false` with a `reason`:
- `spec_status_changed` — spec Status changed between plan and apply; human review needed
- `spec_status_unreadable` — spec.md not found or Status field missing
- `initiative_not_found` — ini_slug absent from workspace.toml
- `entry_not_found_in_queue` — path no longer in the queue (already removed or never present)
- `entry_locator_mismatch` — the registry read under the lock holds no entry at an `intent-brief-drop` or `spec-entry-drop` operation's planned locator, including an entry that is gone, or holds one whose path, kind, or fingerprint differs from the plan
- `entry_not_droppable` — the entry at the planned locator matches the plan but is no longer a repo-origin intent under `docs/product/intents/` or brief under `docs/product/briefs/`
- `entry_not_droppable` (for a `spec-entry-drop` operation) — the entry matches the plan but is no longer a repo-origin spec in a `work.` or `backlog.` collection with empty `needs`
- `policy_move_mismatch` — the `.work-intake.toml` move no longer matches `workspace.toml` or the policy file read under the lock
- `entry_held` — the entry is now held: it is cooled and declares a parent its lifecycle record still lacks
- `cooling_state_unavailable` — a `spec-entry-drop` or `tracker-entry-drop` could not be checked because cooling state is unreadable
- `artifact_write_failed` — a `tracker-entry-drop` could not replace its artifact with the profile table added, so the artifact and the entry are kept
- `entry_not_matched` — a `tracker-entry-drop` entry no longer matches its artifact, or the profile it would copy changed since the plan
- `artifact_changed` — the artifact's bytes differ from the plan's `artifact_sha256`
- `record_not_writable` — the artifact's record could not take the table: the record is not exactly one block, or the re-rendered result does not re-parse to the old record plus the table
- `entry_not_found` — the editable `workspace.toml` has no matching table at the planned locator although the parsed registry does, or an earlier operation in the same run already claimed or removed that entry
- `entry_locator_mismatch`, `entry_not_matched`, `entry_not_found` (for a `captured-entry-drop` operation) — the entry at the planned locator is gone, no longer matches the plan, or an earlier operation of the run already claimed it
- `captured_file_changed` — a `captured-entry-drop` operation's file, or its backing `captured-to-file` record, no longer holds the planned bytes
- `path-invalid`, `path-missing`, `file-cooled`, `record-invalid`, `file-unreadable`, `file-linked`, `slug-invalid` (for a `captured-entry-drop` operation) — the captured file no longer passes the check its plan reason names, so the entry is kept
- `policy_path_unsafe`, `policy_file_exists`, `policy_write_failed`, `policy_read_back_failed` — the `refresh-policy-move` policy file write was refused, and the table is kept
- `entry_has_needs` — the entry still has `needs` after the needs operations ran; resolve them, then re-plan

**`.workspace-repair-plan.json` and temp files** — both are written inside the repo root. Add them to `.gitignore` to avoid accidental commits (the temp files are cleaned up automatically on success).
