## Blockers

**1. `_sentence_containing` does not produce the bounded unit AC-0005 and AC-0006 describe.** `docs/specs/visual-target-field/plan.md:208-213`, `docs/specs/visual-target-field/spec.md:124-131`. The helper bounds only on the two-character sequence `". "` in whitespace-normalized text, so any adjacent markdown structure without a terminal period — a heading, a bullet, a table cell — joins the "sentence". Measured against the real files: inserting the period-free heading `### Commitments require \`visual_target: confirmed\`` immediately above the unchanged sentence at `converge.md:80` yields the unit `"### Commitments require \`visual_target: confirmed\` When an approved visual target exists, write the selected direction's compositional commitments into the doc here"` — AC-0005 passes while the instruction itself stays unscoped. The same edit shape passes AC-0006 on `visualize.md:21`. This is the presence-check mechanism the plan's own `## Construction tests` (plan.md:52-59) says the predecessor tried and rejected, shrunk but not removed. Fix: the criteria's bounded unit must be one the verification can actually isolate — pin a unit the markdown itself delimits (a single source line, a single paragraph block, a single list item) rather than a period-delimited span of normalized text, and state that unit in the criterion so the stub and the criterion name the same thing.

**2. AC-0004's verification is a whole-file presence check, and Testing Strategy misdescribes it.** `docs/specs/visual-target-field/spec.md:120-123` and `:86-91`; `docs/specs/visual-target-field/plan.md:218-219`. AC-0004 says the literals appear "in the instruction that writes the disposition" and "in the instruction covering a target present without a recorded human confirmation", but the stub is `assert "visual_target: confirmed" in converge` / `assert "visual_target: unconfirmed" in converge` — either literal satisfies it from a glossary bullet, a heading, or a reference footer while every instruction stays unwritten. Testing Strategy's grouping claims AC-0004 "asserts an exact literal inside a bounded unit"; it does not. Fix: AC-0004 must name the unit its literals have to appear in, and its verification must assert them there — or Testing Strategy must stop claiming a bounded unit for it.

**3. AC-0013 is an existence check wearing a criterion's clothes.** `docs/specs/visual-target-field/spec.md:153-155`; `docs/specs/visual-target-field/plan.md:250-256`. The criterion says "at least one case asserts the `visual_target` disposition a run is expected to write"; the stub concatenates `evals.json` and `eval_queries.json` into one blob and asserts the substring `visual_target` is somewhere in it. It passes if the string lands in a trigger query or an `expected_output` paragraph, and never touches a case's `assertions` list — which the harness already exposes as a first-class field (`evals[].assertions`, see `packs/experience-design/.apm/skills/creative-direction/evals/evals.json`). Nothing verifies "a case", "asserts", or "a disposition". Fix: the criterion must be verified at the structure the harness actually provides — a named case whose assertion text constrains a specific disposition value — so an eval that merely mentions the field cannot satisfy it.

**4. AC-0010 has no verification artifact.** `docs/specs/visual-target-field/spec.md:143-146` and `:99-101`; `docs/specs/visual-target-field/plan.md:271-275`. Testing Strategy assigns AC-0009/AC-0010 to `tests/conformance/test_pack_metadata.py`, which never opens `docs/product/changelog.md` — its five tests cover pack metadata fields, pack↔plugin version equality, and marketplace schema shape only. `tools/repo/check_release_impact.py` lists `packs/` under `NON_IMPACTING_PREFIXES`, so the CI release gate does not fire for this change either. Nothing checks that a free-standing `##` entry exists, that it carries `### Highlights`, or that the body names the field. T4's Done-when (`make lint-ruff lint-mypy` plus `test_pack_metadata.py`) reads none of it, and does not run `tools/test_build_site_routing.py`, which is what actually enforces the changelog's heading blank-line rule the file's own header describes. Fix: name a verification artifact for AC-0010 that reads the changelog bytes, in a declared mode, and put it in T4's Done-when.

**5. The plan's stub blocks do not meet the stub contract that gates plan approval.** `docs/specs/visual-target-field/plan.md:128-140`, `:142-182`, `:197-203`, `:205-235`, `:245-256`. `packs/core/.apm/skills/work-loop/references/tdd-stubs.md` § *Stub marker convention* requires both halves of one marker: a `# STUB: AC<n>` comment on each test function, and a `Tests:` entry carrying the test function name, its AC identifier and a `stub: true` field — explicitly "not a prose restatement of the behaviour". Every `Tests:` entry here is exactly that prose restatement ("Contract test: the frontmatter carries… Verifies AC-0001") and no code block carries a `STUB:` marker. § *Validate* and § *Record* further require the syntax/compile result and the proven intended red to be recorded in the plan, and § *Validate* fails closed at plan approval when they are not. Neither result is recorded. (I ran the three blocks against the current tree from scratch: all four assertions do go red, so the substance is sound — it is the required record and marker that are missing, and EXECUTE's byte-identity handoff has no marked source to match.) Fix: bring each task's `Tests:` subsection and code block to the marker convention, and record the compile and intended-red results in the plan before approval.

## Concerns

**6. AC-0009's end-state comparison and its third version site are unverified.** `docs/specs/visual-target-field/spec.md:99-105`, `:137-142`. The recorded manual check is defined as two `git show` commands run "at the start of the work", and the plan's Changelog records that baseline — I confirmed it is correct: merge-base carries `4.1.0`, HEAD carries `4.1.1`. But nothing records or checks the *end* state, so the "strictly greater than `4.1.1`" half of the criterion rests on a human reading a version string, with no artifact that records the check performed and the result observed. Separately, the criterion's third site — the `experience-design` entry in `.claude-plugin/marketplace.json` — is covered by neither named artifact: `test_pack_metadata.py` compares only `pack.toml` to `plugin.json`, and the one marketplace-parity test in the tree (`tests/roster/test_atlassian_marketplace_version_parity.py`) is scoped to a different pack and lives in a dispatch-only suite. Fix: AC-0009 needs a verification that observes the post-bump state across all three sites and records its result, not only a start-of-work baseline note.

**7. AC-0002's forbidden-literal list is not the constraint the privacy rail states.** `docs/specs/visual-target-field/spec.md:113-116`, `:77-79`; `docs/specs/visual-target-field/plan.md:159-162`. The rail forbids "a person's name, handle, or contact detail"; the criterion bans four English word-tokens. `<approver>`, `<confirmed by>`, `<signed off by>`, `<person who approved>` (tokens: person, who, approved — `who` is banned, but `<approver>` is not) and `<role and initials>` all pass the check while inviting exactly the content the rail forbids, so the criterion's stated purpose ("so the placeholder cannot invite the content the `Never do` rail forbids") is not delivered. Compounding it: `converge.md` is the surface that tells a producer what to put in the confirmation record, and no criterion constrains what it says. Fix: state the constraint as the property the rail names rather than as a four-word denylist, and decide whether the producing instruction needs a criterion of its own.

**8. AC-0002's stub is stricter than the criterion, in the direction that reds a conforming template.** `docs/specs/visual-target-field/plan.md:159`. The criterion says the placeholder "names the confirmation's date and where it was recorded"; the stub asserts the literal strings `date` and `where` are in the line. A conforming placeholder such as `**Confirmation record:** <YYYY-MM-DD> — <location of the record>` satisfies the criterion and fails the test. The spec's own Testing Strategy says these criteria assert *exact literals*, so the two documents disagree about what is contracted. Fix: either the criterion names the literals the verification pins, or the verification stops pinning literals the criterion does not name.

**9. AC-0007's bounded unit is drawn from a different file set than the criterion names, and uniqueness is unchecked.** `docs/specs/visual-target-field/spec.md:132-134`; `docs/specs/visual-target-field/plan.md:229-234`. The criterion pins "the single list item beginning `- **Approved visual target**`" in `creative-direction`'s `SKILL.md`; the stub splits `_skill_text()`, which concatenates eight files (SKILL.md, the template, and six references — `test_contract.py:72-84`), and takes the first `next()` match. It happens to land on `SKILL.md:92` today only because SKILL.md is first in the concatenation. The same unchecked-uniqueness gap applies to `_sentence_containing`, which calls `flat.index(needle)` and silently takes the first occurrence while both AC-0005 and AC-0006 say "the single sentence". Fix: the verification must read the file the criterion names, and must establish the singleness the criteria assert rather than assume it.

**10. AC-0005 keeps the field-literal form the rail's carve-out does not cover.** `docs/specs/visual-target-field/spec.md:124-126`, `:71-75`. The `Never do` rail exempts "an instruction that tells a producer when to *write* the field". AC-0005 requires `visual_target: confirmed` inside the sentence that tells the producer when to write *compositional commitments* — a different write, conditioned on the field's value. AC-0006 and AC-0007 were reworded in this revision to the human-confirmation form precisely to avoid a field read; AC-0005 was not, and the spec does not say why the asymmetry is safe. An implementer facing "write commitments when the artifact reads `visual_target: confirmed`" has no ruling on whether that crosses the rail. Fix: state whether conditioning a non-field write on the field's value is inside the carve-out, and align AC-0005's required form with that answer.

**11. The spec's Outcome contradicts what the plan actually ships.** `docs/specs/visual-target-field/spec.md:20-27` against `docs/specs/visual-target-field/spec.md:124-126` and `docs/specs/visual-target-field/plan.md:283-284`. Outcome says "no existing behaviour changes", but T2 changes when `converge` writes compositional commitments (today `converge.md:80` writes them whenever "an approved visual target exists"; after T2 it writes them only for a confirmed target), and T4 justifies a `### Highlights` subsection on the ground that "the change alters what a consumer can do". Both cannot be true. Outcome is working material by the spec's own tiering, which is why this is not a Blocker, but the release-facing decision in T4 rests on the opposite reading. Fix: make Outcome say what changes for a producer, so the Highlights call and the contract agree.

**12. AC-0012 cannot establish what it says it establishes.** `docs/specs/visual-target-field/spec.md:149-152`; `docs/specs/visual-target-field/plan.md:172-182`. The criterion's stated purpose is that "the re-derived excerpt demonstrably carries the new material", but the check is whole-file containment over a 439-line guide that already discusses the template in prose outside the fenced excerpt (e.g. `guides/experience-design/how-to/establish-design-intent.md:33`). Both literals could land in that prose and pass while the excerpt is untouched; the guidebook lint (`_appears_verbatim_in`, `tools/lint-guidebook-steps.py:670-690`) only proves *some* contiguous run matches, which is the hole AC-0012 exists to close. The excerpt does reach the `## Approved visual target` section (guide lines 136-217 mirror template lines 1-84), so the criterion is satisfiable at the right scope. Fix: scope AC-0012's assertion to the fenced excerpt block rather than the file.

**13. The release procedure cites a section that is not in the file the plan names, and silently deviates from the one that is.** `docs/specs/visual-target-field/plan.md:5-8` and `:279-283`. § Landing changes lives in the **root** `AGENTS.local.md:49-62`, not `packs/AGENTS.local.md`, whose sections are Self-hosting projection (insider notes), Marketplace and release pipeline, the confinement-helper note, the portable-content rule, and Self-hosting projection. Meanwhile `packs/AGENTS.local.md:26-29` § Marketplace and release pipeline — the section that actually governs a pack release — prescribes `FORCE=1 make build-self` at step 2, and the plan's chosen procedure departs from it without naming the step it departs from. The commit-first sequence is defensible; the citation chain behind it is wrong. Fix: cite the owning file for each rule, and record the deviation against the release-pipeline step it deviates from.

**14. The follow-on has no stable artifact or register entry.** `docs/specs/visual-target-field/spec.md:157-161`. `spec-and-plan-contract.md:110-115` requires a follow-on to carry "an owner and stable work-intake artifact or external evidence reference"; this one carries an owner and the words "not yet authored", and `workspace.toml` holds no `visual-target` entry.
