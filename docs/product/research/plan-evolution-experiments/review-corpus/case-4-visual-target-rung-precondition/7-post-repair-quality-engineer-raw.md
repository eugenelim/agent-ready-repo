## Blockers

**1. The guard negative test provably does not describe the promoted bytes, and the handoff says it does.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_run.py:29-31`. `t13_negative_test.py` runs as step 10, before `__converge__` (step 11) re-runs `t13_digests.py` and `t13_report.py`. The shipped record proves the bytes then moved: `state/guard-negative-test.json` reports `digests_before` = `digests_after` = `md sha256:bbc4f71a…`, `json sha256:93305e69…`, while `state/promotion-record.json:5-8` records the promoted `md sha256:f3255b75…`, `json sha256:c8ce42b3…`, and `state/run-order.json` shows convergence pass 1 with `changed: true`. `t13_report.py:105-107` asserts the opposite in a comment: "Written before the convergence loop's final report pass, so the copy the candidate records is current." This is the exact staleness class round 6 sustained against the embedded lint, reintroduced for the guard test and then claimed current. Fix: the guard demonstration must be bound to the bytes that were promoted — either drive it after the fixed point is reached, or have promotion refuse unless the negative-test record's digests equal the candidate digests.

**2. `all_guards_demonstrated: true` is published while 2 of the 13 named checks were never injected.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_negative_test.py:34-65` defines 11 cases; `tools/t13_lint.py:43-57` publishes 13 `CHECK_NAMES`. The uncovered two are `same-quantity-two-answers` and `round-breakdown-does-not-sum`. Nothing compares the case set to the check set, so `cases: 11` sits beside `checks: 13` in the handoff with no signal, and `guards_that_did_not_fire: []` cannot name a check that was never driven. Fix: make the negative test fail when its injected-class set does not cover the lint's published check set, so an added check without a case cannot pass silently.

**3. Two of the published checks are identities that cannot fail.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_lint.py:171-174` tests `sum(rs["by_round"].values()) != rs["findings_filed_total"]`, but `t13_report.py:302,306` set both from one call: `findings_filed_total = r["filed_total"]` and `by_round = r["by_round"]`, and `t13_derive.py:107,111` compute those as `sum(r["filed"] …)` and `{r["round"]: r["filed"]}` over the same list. The comparison holds for any distinct round numbers. `t13_report.py:1861-1863` has the same shape: `rv["filed_total"] != rec["review_status"]["findings_filed_total"]` compares a value to itself, and it is one of the emission gate's advertised 5 checks. `t13_derive.py:112-114` publishes the same identity as `breakdown_sums_to_filed_total`. This is the "two compared literals from the same function" defect round 5 named, reintroduced in the round-6 instruments and then counted as coverage. Fix: compare each stated count to an independent source — the raw report files each round names, or a stored per-round tally — or drop the identities and reduce the published check counts to checks that can fail.

**4. `restoration_verified_by_digest` gates nothing, though the handoff lists it as bound at promotion.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_negative_test.py:117,133,137`: `restored_ok` is recorded but excluded from `all_guards_demonstrated`, and the exit path fails only on `all_guards_demonstrated`. `tools/t13_promote.py:62-70` then checks only the `all_guards_demonstrated` key. So a failed restoration is reported as a field and acted on by nobody, while the promoted JSON's `current_byte_controls.controls_bound_at_promotion` lists "guard negative test, with restoration verified by digest" and `emission_gate.candidate_dependent_controls_gated_at_promotion` lists "guard negative test and its digest-verified restoration". Round 6 made the claim falsifiable and left it unenforced. Fix: a false restoration must fail the negative test and refuse promotion, or the two claims must stop saying restoration is gated.

**5. A normative carry entry disappears silently when the file is absent.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_report.py:97-108` lists `state/process-launch-log.json` in `EXTRA_CARRY`, whose own comment explains these were added because "Round 1 omitted the first four, so AC-0021, AC-0023 and AC-0024 reduced to self-asserted booleans after integration." `t13_report.py:140-142` then filters on `if p.exists()`. Fix: an `EXTRA_CARRY` entry that does not resolve must either fail emission or be recorded as a named, reasoned absence in the manifest.

## Concerns

**6. The promotion gate's refusal branch has never been exercised.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_promote.py:41-89`. Eight distinct problem conditions guard the only path from candidate to promoted bytes — screen exit, lint exit, `screen.clean`, `lint.clean`, `lint.target`, `lint.md_bytes`, and four control-record keys — and none has been observed to fire; `state/promotion-record.json` records `promoted: true` with `problems: []`. Every other guard in this pipeline got a forced negative case; the gate on which the whole round-6 repair rests did not. The code reads correctly, so the gap is demonstration rather than a located defect. Fix: add forced-refusal cases that make each promotion condition fail against copies and assert the exit is non-zero and the promoted paths are untouched.

**7. The lint's seeded-taxonomy regex misspells one of the three answer-key class ids, so that third of the check is inert.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_lint.py:180-181` matches `degenerate-decision`; the registry's actual id is `decision-degenerate` (`sealed/hidden-registry.json`, 12 occurrences; `tools/t13_registry.py:35,59`; `tools/t13_mutate.py:62`). A carried artifact naming `decision-degenerate` passes the `seeded-taxonomy-in-carried-artifact` check, and the negative case at `t13_negative_test.py:47-48` injects `amendment-digest defect`, the one spelling the regex does hold, so the demonstration cannot expose the gap. `tools/t13_screen.py:25` carries the correct spelling and screens the same targets, which is why the disclosure outcome is currently still protected. Fix: derive both vocabularies from `t13_registry`'s class table instead of re-spelling them, so a class cannot exist that a guard does not know.

**8. The disclosure screen's recipe detector is narrower than the property it claims to screen.** `.context/experiments/codex-headless-sol-loop-confirmation-r1/tools/t13_screen.py:32,51`: `RECIPE_KEYS.issubset(set(o))` requires all seven of `defect_class, invariant, field, leaf, edit, repair, slot`. **10.
