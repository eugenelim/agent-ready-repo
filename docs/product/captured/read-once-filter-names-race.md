# Read-once filter names race the next Git call

- **Status:** Open
- **Kind:** defect

The work-loop brief runner and the supervisor's Git helper both read the repository's `filter.<name>` keys once, then empty those names with `-c filter.<name>.clean=` overrides on later Git calls. That read and the filter-capable call that follows (the runner's base-check `git status`; the supervisor's `HardenedGit` calls) are separate processes. A worker that can write the shared Git directory can loop three steps: set `filter.evil.clean=<cmd>`, unset it, and back-date the index while `* filter=evil` sits in `.git/info/attributes`. Roughly 1 call in 10, the clean command then runs as the operator in the gap. Git has no flag that turns off every filter: `--attr-source=<empty tree>` and `core.attributesFile=/dev/null` still leave `.git/info/attributes` in force (checked on Git 2.56).

The same actor can also forge the main index's cached stat data for a path, keeping its base blob id, so `git status` reads an edited `docs/` file as unchanged (finding S7, accepted with this item on 2026-11-07). The fix must cover both callers together, because the runner launches the supervisor's `status` and `gates` in every slice worktree. One route is to stop using filter-capable commands for change detection: compare working-tree bytes with `git hash-object --no-filters` against tree entries, list untracked files with `git ls-files --others`, and judge line-ending-converted checkouts explicitly. Accepted as risk for the brief-level runner on 2026-11-06 by risk-owner eugenelim. The precondition is a worker with write access to the shared Git directory racing that loop. Source: spec `docs/specs/brief-level-runner/spec.md`, restarted-run review round 2, finding S5.
