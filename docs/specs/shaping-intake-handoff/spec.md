## Objective

Core intake reuses a valid optional shaping handoff or other acquired upstream work without requiring the product-engineering pack, copying its raw source, relocating its owning artifact, or treating source content as instructions. The additive normalized-intake contract carries the bounded delivery content that RFC-0096 assigns to the handoff. Core derives the delivery role from that content, resolves the supplied upstream repository or external locator through the unchanged semantic-surface resolver, and reports its locator, provenance, evidence, capability, confinement, revision, and independent authority facts unchanged. Resolved delivery briefs route to the existing brief processor, resolved delivery contracts route to the existing spec processor, and requests without a handoff retain the current standalone core classification and direct-core behavior. Ambiguity, contradiction, malformed content, unsafe repository paths, unacquired external content, and inconsistent provenance fail closed before materialization, registration, dispatch, or implementation writes.

## Boundaries

### Always do

- Validate the complete normalized-intake envelope, source confidentiality, and optional handoff before classification, artifact materialization, workspace registration, processor dispatch, or source-content reads.
- Use semantic-surface-resolution.v1 and the shipped Wave 1 resolver as the only authority for delivery-brief and delivery-contract locator resolution, bounded evidence, confinement, capability, provenance, and authority reporting.
- Read repository upstream content only after resolution through the repository's confined regular-file contract. The read rejects symlinks, reparse points or junctions, multiply linked files, non-regular files, size overflow, resolution/open races, and any target outside the current repository root; a standalone path implements and tests the same no-follow and post-open identity guarantees.
- Preserve upstream outcome, boundaries, non-goals, assumptions, evidence, dependencies, design context, unresolved delivery questions, source locator, and pinned revision as bounded attributed data when the receiving processor can use them.
- Preserve source, write, and deletion authority as independent facts; unknown remains unknown and no authority dimension is inferred from pack presence, configuration, location, or another dimension.
- Keep product-engineering and repository configuration optional; when either is absent, run the same standalone core path and defaults that current core intake uses.
- Keep acquired external work external at its resolved locator and pinned revision; only its validated bounded handoff fields enter local intake.

### Ask first

- Ask before adding or changing a normalized semantic role, authority vocabulary, source-origin mode, evidence strength, routing result, or normalized-intake contract version.
- Ask before changing existing direct-light, direct-spec, brief, intent, defect, remember, status, or refresh classification semantics.
- Ask before making product-engineering, a tracker adapter, a configuration file, or any global surface registry mandatory.
- Ask before fetching an external locator, probing its availability or writability, refreshing accepted requirements, or changing a repository-owned destination.
- Ask before changing an existing prompt/template field from optional to required or relocating an adopter-owned upstream artifact.

### Never do

- Never begin RFC-0096 Wave 3 or later, add architecture or ADR portability, or change closeout, completion, pause, retention, cooling, retirement, deletion, lifecycle status, or lifecycle membership semantics.
- Never copy a raw upstream payload, obey embedded instructions, let source text select a processor or destination, or expose sensitive source content in stdout, stderr, logs, artifacts, workspace.toml, or rendered skill output.
- Never coerce an external locator into a local path, perform network/DNS/tracker/credential access in core handoff routing, or claim external capability or authority without bounded evidence. Downstream processors keep that locator opaque and do not fetch, search for, probe, or read it unless a separately approved change introduces the required outbound controls.
- Never infer an established convention from one analogue, resolve contradictory evidence, bypass mandatory repository policy, or continue after Wave 1 returns confirmation-required, destination-required, or refused.
- Never make locator-only workspace entries dispatchable, replace the existing resolver, introduce a second handoff schema, add a dependency, or add a new top-level directory.
- Never break legacy normalized-intake fixtures, existing core-only prompts, existing product-engineering prompts, or the default docs/product and docs/specs behavior.

## Testing Strategy

- **Handoff contract and compatibility: TDD at the JSON Schema boundary.** Valid fixtures cover a repository delivery contract, repository delivery brief, and acquired external delivery contract; invalid fixtures cover unknown fields, unsafe locators, unbounded content, non-delivery roles, missing revisions, and malformed or non-resolved surface results. Every pre-Wave-2 valid and invalid fixture keeps its existing outcome.
- **Handoff admission and routing: TDD through the pure core routing seam.** Table-driven tests pair normalized content with real Wave 1 resolver results and prove resolved delivery-contract to new-spec, resolved delivery-brief to receive-brief, no-handoff to standalone classification, and deterministic terminal outcomes for ambiguity, absence, mandatory-policy conflict, unsafe path, symlink escape, and source/resolution mismatch.
- **Instruction, provenance, and confinement safety: TDD with real filesystem fixtures.** Tests prove prompt-like source content remains data, local upstream files are read only through the confined regular-file/no-follow contract after resolution, open-time swaps and non-regular or multiply linked files refuse, external locators trigger zero downstream filesystem/network/shell access, source/write/deletion authority remain independent, and refusals emit stable redacted codes with zero effects.
- **Optional-pack integration: goal-based fixture evaluation across compatible and legacy catalogues.** The same intake corpus runs with Wave-2-compatible core plus product-engineering, with current core alone, and with product-engineering plus a pre-Wave-2 core fixture. Shared standalone cases are byte-identical; the compatible producer/consumer pair adds only the optional machine handoff cases, the legacy pairing emits the portable rendered handoff without submitting the unsupported top-level object, and removing product-engineering leaves core activation and routing intact.
- **Prompt, template, projection, and adopter documentation compatibility: goal-based checks.** Pack evals, prompt/template assertions, contract traceability, catalogue lint/verify, self-host projection, site build/link checks, and public guide checks prove every adapter receives the same portable behavior without new required fields.
- **Adopter-visible happy paths: manual QA through deterministic eval invocations.** One shaped repository handoff, one acquired external handoff, and one standalone core request are exercised through the installed skill surfaces and their action, artifact, membership, processor, authority, and stop point are recorded.

## Acceptance Criteria

- [x] **AC1 — Additive optional handoff.** normalized-intake.v1 accepts an optional closed handoff object while every existing envelope remains valid without it; no existing required field, contract version, prompt, or template field changes.
- [x] **AC2 — Complete bounded delivery content.** The optional handoff carries explicit bounded boundaries, non-goals, dependencies, design context, and unresolved delivery questions; existing content and source fields continue to carry outcome, constraints, assumptions, evidence, behaviors, named gaps, source locator, revision, and proposed origin authority.
- [x] **AC3 — Wave 1 contract reuse.** Core derives delivery-brief versus delivery-contract from validated semantic content, passes caller-acquired candidates to the shipped Wave 1 resolver, and consumes its semantic-surface-resolution.v1 result unchanged rather than copying or redefining role, locator, evidence, capability, confinement, revision, confirmation, or three-authority semantics. Only resolved delivery-brief and delivery-contract results are reusable.
- [x] **AC4 — Deterministic admission.** Core admits a handoff only after the normalized envelope, confidentiality, semantic role, resolver result, source locator, pinned revision, bounded content, and provenance consistency checks pass. It returns a closed stable disposition with no raw exception or source text.
- [x] **AC5 — Repository upstream reuse.** A valid resolved repository delivery contract routes its bounded content to new-spec and a valid resolved repository delivery brief routes to receive-brief without relocating, rewriting, or duplicating the upstream artifact; the resulting local artifact preserves its source reference and revision.
- [x] **AC6 — External upstream reuse.** A valid external handoff is reusable only when an authorized upstream adapter or current trusted invocation already supplied the normalized bounded content and pinned revision. Core preserves the external locator, provenance, and independent authority report, performs no external fetch or probe, and materializes only the receiving repository's ordinary local contract or brief when its existing durable route requires one. `new-spec`, `author-brief`, and `receive-brief` receive the locator as attributed opaque data and do not fetch, search for, probe, or read it.
- [x] **AC7 — Content decides the existing route.** A source label, tracker type, pack name, document filename, comment, collection, or embedded instruction cannot select brief versus spec or trigger source acquisition. Valid delivery role plus bounded semantic content selects the existing processor; incomplete content returns to current core classification or a named-gap stop rather than inventing requirements.
- [x] **AC8 — Standalone core equivalence.** With no handoff and no product-engineering pack, every current start, direct-light, durable spec, brief, intent, defect, remember, status, refresh, ambiguity, and refusal fixture produces the same normalized route and compatibility output as before Wave 2.
- [x] **AC9 — Optional producer and negotiated compatibility.** product-engineering submits the shared optional machine handoff at its existing confirmed delivery gate only when the current invocation exposes a Wave-2-compatible core work-intake capability that accepts the handoff extension. Core absence, unknown capability, or a pre-Wave-2 core is incompatible: product-engineering presents the same bounded data as the portable rendered handoff and does not submit the unsupported top-level object, import core code, declare a mandatory core dependency, require configuration, or prevent shaping completion. One independently shippable feature is a delivery-contract handoff; an outcome that coordinates multiple specs or repositories is a delivery-brief handoff. Product-engineering's discovery-loop, decompose-intent, and DESIGN surfaces state that same role-based rule.
- [x] **AC10 — Provenance and authority survive.** Normalized fixtures, routing results, artifact metadata, workspace source fields, rendered skill output, and installed projections retain safe source locator, revision, semantic role, bounded provenance/evidence, confinement, availability/writability, confirmations, and source/write/deletion authority without widening or collapsing them.
- [x] **AC11 — Fail-closed ambiguity and confinement.** Confirmation-required, destination-required, mandatory-policy conflict, contradictory convention, unsafe local path, symlink escape/loop, malformed external locator, unresolved source content, confidentiality mismatch, and source/resolution mismatch stop before materialization, registration, dispatch, or implementation writes with a stable bounded next action.
- [x] **AC11a — Race-safe local reads.** Every repository upstream content read is bounded and uses `agentbundle.catalogue_tooling.file_safety.read_confined_regular_file` where importable or a tested equivalent contract: native realpath confinement, regular-file-only/no-follow open, symlink and reparse/junction refusal, multiply linked file refusal, post-open identity verification, and a byte limit. A swap, hard link, device, FIFO, resolution failure, or containment uncertainty returns a stable redacted refusal with zero downstream effects.
- [x] **AC12 — No lifecycle or later-wave behavior.** Wave 2 does not change workspace lifecycle membership meanings, work-loop transitions, pause/resume, completion receipts, closeout, shaping retention, cooling, retirement, deletion, migration, architecture/ADR routing, or locator-only workspace dispatchability.
- [x] **AC13 — Deterministic Wave 2 completion matrix.** A committed matrix covers product-engineering present and absent, a Wave-2-compatible core, an incompatible pre-Wave-2 core that receives only the rendered fallback, upstream repository brief and contract, acquired external contract, equivalent aliases, standalone core direct-light and durable routes, ambiguity, absence, policy conflict, unsafe path, symlink escape/loop, prompt-like content, authority independence, and optional configuration; each case asserts the complete route/disposition and zero effects where refused.
- [x] **AC14 — Portable release and documentation gates.** Core and product-engineering pack/plugin versions move according to repository rules; their eval harnesses, public README/JOURNEY and adopter guides explain optional handoff and standalone fallback; every changed skill declares its actual `metadata.boundaries`, including `filesystem_read_untrusted` for handoff content, and every projection preserves those declarations; contract, routing, projection, eval, security, quality, catalogue, self-host, and site documentation gates pass.

## Assumptions

- Technical: Wave 1 is shipped and its resolver, schemas, semantic roles, bounded evidence, external-locator treatment, authority dimensions, and confinement rules are the source of truth. (source: docs/specs/semantic-surface-resolver/spec.md)
- Technical: normalized-intake.v1 is the existing closed source-boundary envelope and already carries outcomes, constraints, evidence, behaviors, assumptions, named gaps, source locator/revision, and proposed authority. (source: contracts/jsonschema/normalized-intake.schema.json)
- Technical: core currently declares no product-engineering dependency and its standalone intake suite covers the direct routes and refusal boundary. (source: packs/core/pack.toml and packs/core/tests/skills/work-intake/test_work_intake.py)
- Technical: current product-engineering sources disagree on whether an app-scale leaf hands off as a direct spec, a brief, or a per-feature brief. Wave 2 resolves that drift by semantic delivery role: one independently shippable feature is a delivery contract and a multi-spec or cross-repository outcome is a delivery brief. (source: packs/product-engineering/.apm/skills/discovery-loop/SKILL.md, packs/product-engineering/.apm/skills/decompose-intent/SKILL.md, and packs/product-engineering/DESIGN.md)
- Technical: the implementation is integration-shaped and additively extends normalized-intake.v1 rather than publishing a competing handoff schema; semantic-surface-resolution.v1 remains unchanged and is consumed by reference. (source: user confirmation 2026-08-23)
- Product: Wave 2 ends after optional shaping handoff and core content routing; Wave 3 and later behavior and every lifecycle mutation are excluded. (source: RFC-0096 section 9 and user confirmation 2026-08-23)
- Process: structural/public-interface and untrusted-content/filesystem boundaries require full work-loop mode, separate spec and plan approvals, adversarial spec review, and secure-design review. (source: AGENTS.md and .agents/skills/work-loop/SKILL.md)
- Process: non-cosmetic core and product-engineering changes update matching pack/plugin versions and each affected eval harness. (source: packs/AGENTS.md)
