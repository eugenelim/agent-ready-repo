## Blockers

**1. `outline` lists value nodes, breaking CRIT-3.** `evals/files/preservation-review/graph.py:54-56`. CRIT-3 (`spec.md:9`) says default listing excludes value nodes, but `outline` is the listing consumer of the graph and still emits every node, value nodes included; only `search` (`graph.py:45-51`) got the new `VALUE` filter, so the new node kind leaks into an existing reader the change did not update. Run: `python3 -I -c "import sys; sys.path.insert(0,'.'); from graph import *; print(outline(build(['def run','call run','value limit','call limit'])))"` from `evals/files/preservation-review/` printed `['def run', 'call run', 'value limit', 'call limit']`. Fix: the default listing path must leave out value nodes, as CRIT-3 requires, while the `def` and `call` lines keep their build order; any opt-in to see values must be explicit, the same way `search` uses `include_values`.

**2. CRIT-3 has no verification artifact.** `evals/files/preservation-review/test_graph.py:23-26`. No test checks that default search leaves out a value node, and no test calls `outline` at all (`grep -n "outline\|include_values" test_graph.py` found no match, exit 1). The only search test looks up `"run"`, a name with no value node, so it would still pass if the `VALUE` filter at `graph.py:50` were removed. Fix: CRIT-3 needs a test for each default consumer, `search` and `outline`, using an input that has a value node, where the expected output is written out by hand and does not come from the code under test, so the test fails if either consumer starts to show value nodes.

## Concerns

**3. CRIT-2 test takes its expected side from the resolver under test; referral to quality-engineer.** `evals/files/preservation-review/test_graph.py:14-20`. The CRIT-2 (`spec.md:8`) test builds `expected` from `resolve_calls(graph)` itself, so it compares the function with itself and cannot fail. The code does meet CRIT-2 today: the run above printed `{'run': [Node(name='run', kind='def')], 'limit': []}`. But nothing would catch a change that started matching value nodes. Judging test strength belongs to quality-engineer, so this is a referral, not a strength finding. Fix: get a quality-engineer pass on the CRIT-2 test before completion, and record that the expected side comes from a written-out table and not from `resolve_calls`.

**4. Spec status not moved for implementation.** `evals/files/preservation-review/spec.md:3`. The status is still `Approved` while the implementation lands, and the spec metadata contract says an implementation run moves the spec to `Implementing`. This is metadata drift (a). Fix: the spec status must match the change: `Implementing` while CRIT-3 is unmet, and `Shipped` only once every criterion is met.

**5. Acceptance criteria are not task-list items.** `evals/files/preservation-review/spec.md:7-9`. CRIT-1 to CRIT-3 are plain bullets, but the spec metadata contract requires each one to be `- [ ]` or `- [x]` (or to carry a deferral marker), so it cannot be decided whether each criterion is done. This is metadata drift (b). Fix: each criterion must use task-list notation that shows its real state; CRIT-3 stays open until findings 1 and 2 are fixed.
