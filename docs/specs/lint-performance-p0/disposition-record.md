# Resolve-vs-surface disposition record

Opened at PLAN, closed at DECIDE, per the `work-loop` self-coverage gate. The
rule it implements: between human gates, resolve everything a referent can
resolve, and surface only the irreducible.

## Surfaced to the human (irreducible)

| # | Item | Why it could not be resolved here |
| --- | --- | --- |
| S1 | **Measured 3-file scope** vs the brief's wider net | The brief named seven P0 patterns; measurement found only three files carrying one. Narrowing scope is the requester's call, not the implementer's. Resolved by human choice. |
| S2 | **One repo-only resolver** instead of the brief's portable `agentbundle` helper | The brief mandated a package-local implementation. ## Resolved without surfacing

Each of these was a real question that a referent could settle from the
repository, a probe, or measurement — so it was settled rather than escalated.

| Item | How it was resolved |
| --- | --- |
| Does `check-ignore --stdin` parse pathspec magic? | Probed git 2.50.1 directly: `:!x`, `:(exclude)x`, `:(glob)x`, `:(icase)x`, `:(attr:…)x` each exit 128 while echoing candidates processed before them. `:(literal)` is rejected outright, so it is not an escape hatch. |
| Is a partial result on exit 128 safe to use? | No — verified that git echoes what it processed before failing. Made a hard error rather than a policy outcome. |
| Can a hostile `core.excludesFile` corrupt a capture? | Yes, verified: with `GIT_CONFIG_COUNT=1` pointing it at a hostile file, `check-ignore` reported an extra path ignored and exited **0**. Closed the channel and asserted identical bytes under a deliberately hostile global ignore. |
| Which env channels leak into a Git subprocess? | Enumerated and closed: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, `GIT_CONFIG_PARAMETERS`, and the four pathspec vars. `GIT_CEILING_DIRECTORIES` is **set**, not unset — unsetting it widened discovery, the opposite of hardening. |
| Would one shared resolver or three be right? | Measured caller counts per distribution boundary; one, per S2. |
| Is `_NO_RUNNER`/`_RUNNER_FILES` churn a real gate hazard? | Reproduced it: adding a `_NO_RUNNER` entry reddened 18 of 22 fixtures and `--regenerate` could not clear it. Fixed by redacting ambient state, and every property of the redaction is pinned by a mutation that reddens the suite. Two of the original pins were themselves replaced in review round 3 — see the last row. |
| Is the `_RUNNER_FILES` case fixable the same way? | No, but not for the reason first recorded. Its added `FAIL: runner file …` lines **are** redacted; what cannot be is the consequence — the missing file fails `runners-keep-suites-isolated`, so that check's `ok` line disappears from all 22 baselines, and no redaction restores an absent line. Neutralising it would also mean weakening a fail-closed staging guard or writing into a staged `tools/`. Recorded as a re-pin trigger instead of overstated as fixed. |
| Did the `selftest-mutates-tracked-makefile` hazard fully close? | No. Tracked-file mutation is gone (2 real `Makefile` rewrites → 0); two **untracked** plants remain for one lint launch each, so a concurrent `git add -A` can still stage one. Recorded as P1 residual 4 and, so the mechanism outlives this spec, as the `selftest-untracked-plant-window` slug in `workspace.toml [backlog].open` — rather than counted as closed. |
| Was the SAST failure caused by this diff? | No — `pip-audit`'s `ensurepip` failed against a full host disk. Re-run after freeing space: exit 0, full SAST. Both runs recorded so the first is not misread as real. |
| Do my own new assertions actually discriminate? | Checked by mutation, and **ten did not**, across rounds 2–7. The number is stated on one criterion — *the assertion could not fail, or did not exist at all* — and reached it in three corrections, from four to nine to ten, each time because it was reconstructed from memory instead of kept as a list. **Round 2:** a summary assertion was `all()` over an empty sequence; a Windows-path assertion could not tell `str` from `as_posix` on POSIX. **Round 3:** a "trusted runner path" check compared a hand-copied literal against the constant it was copied from. **Round 5:** the intra-finding sort had no assertion; the FAIL-before-non-FAIL ordering was neither listed nor asserted; the "surface is stripped" assertion could not fail for the property its name claimed. **Round 6:** the round-4 launch-directory fix had no assertion, and the cwd-restore assertion was vacuous from the repo root — the only directory CI launches from. **Round 7:** the line-terminator fold, the behaviour that lets a POSIX-captured baseline compare on Windows, had nothing holding it — switching `splitlines()` to `split("\n")` left the structural suite *and* the golden gate green. And the strongest case: extracting a helper carried the floor check and summary out of `main()`, so `main()` returned `None`, `SystemExit(None)` exited **0 on every failure**, and the suite still printed `ok — 31 cases passed`. A required-chain gate that cannot fail is worse than no gate; it was found by mapping the module's AST, not by reading its output. Deliberately **excluded** as a double-count: round 3's tally erasure, which had its own row below and is a different defect — that assertion *could* fail, it asserted the wrong thing. Counting it gives eleven. All ten replaced with assertions proven to fail under mutation. **The lesson: writing an assertion is not evidence it can fail, and neither is watching it pass.** |
| Was erasing the failure tally the right call? | No — reversed in round 3. The lint prints one `FAIL:` line per finding then `len(findings)`, so `original − redacted` is exact. Erasing it discarded the one signal the compared surface must keep: a finding appended twice but printed once, which is what the memoised runner parse could regress into. Now subtracted precisely, which also made a contradicting spec section true again instead of needing an amendment. |
| Should `refused` and `refused_by` both be stored? | No. Two fields for one fact admit `refused=True, refused_by=None`, which fell through to the git wording and reinstated the misattribution the field was added to prevent. `refused` is now derived from a `RefusalSource` enum, so the bad pair is unrepresentable. |
