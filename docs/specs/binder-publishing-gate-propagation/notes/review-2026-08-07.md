### The finding that changed the decision

**A build-time `<figure>` wrapper inserts lines around every diagram, so the
single-integer `line-offset` breaks.** The first draft of D46 specified
`<figure role="group" aria-label="…">` + `<figcaption>` around each fence — verified
working in a browser, but verified for the wrong property. `zensical-adapter.md`'s
per-file transformation rests on *only the frontmatter and heading steps change line
counts*, and `resolved-index.md` names a length-changing body transformation as
exactly the condition that brings the Quarto `line-map` breakpoint array back.
Inserting lines per diagram is that condition. The reviewer also noted the wrapper
names a *container* rather than the graphic, and has no `accDescr` equivalent.

**Disposition: `apply`, by re-planning the mechanism and re-verifying it.** Rather
than accept either cost, a third route was measured (Z6f, Z6h, Z6i): the compiler
emits `data-a11y-name` / `data-a11y-desc` on the fence's **opening delimiter** via
`attr_list` — a same-line rewrite, so zero added lines — and the theme lifts them
into the Mermaid source as `accTitle:`/`accDescr:` before the bundle mounts, so
Mermaid generates `<title>`/`<desc>` inside the SVG. Measured
`role='graphics-document'` carrying **both** name and description, diagram rendered,
zero remote requests, no page errors. Better than both earlier routes on every axis
the reviewer raised.

**And chasing it turned up Z6h, the widest-reach finding in the whole run:**
`attr_list` attribute values terminate on `"`, so a label of
`Diagram & "3.1" <script>x</script>` put a **live `<script>` into the published
page**.

> **The control drafted here was wrong, and pass 3 caught it.** This paragraph
> originally continued: *"Escaping is not an adequate fix — it stops the breakout but
> double-encodes, and Mermaid's `accTitle` grammar then truncates at `<`. The control
> is an allowlist."* Re-measurement disproved both halves. Escaping round-trips
> exactly; `<` does not truncate. See pass 3 for the control that survived
> measurement.

## Pass 3 — `adversarial-reviewer` (the permitted Blocker re-review)

Seven blockers, six concerns, three nits. **Two of them corrected my own evidence,
which is the outcome that justified running a second pass at all.**

**The finding that mattered most: my stated reason for a security control was wrong.**
I had written that HTML-escaping an `attr_list` value "double-encodes", and specified
an ASCII allowlist on that basis. The reviewer reproduced it and found escaping
round-trips exactly. **Re-measured and confirmed the reviewer, then went further than
the reviewer:**

- A single escape round-trips `Ledger & payments "3.1" — l'architecture réseau`
  character for character. The allowlist was **gratuitously destructive** — it would
  have mangled `Réseau` and dropped 漢字, silently, in the one class of string that
  exists to be read aloud.
- The reviewer's proposed replacement reason — that Mermaid's `accTitle` grammar
  truncates at `<` — **also did not hold**: `<b>angle</b>` survived intact.
- What *did* hold, measured: **`%%{init:{"theme":"dark"}}%%` is consumed as a Mermaid
  directive** (the construct the scanner rejects in authored bodies, arriving through
  a channel it never inspects), and **an embedded newline destroys the diagram.**

So the control is **HTML-escape, plus reject on `%%{` or a newline** — every clause
measured. The uncomfortable part is worth recording plainly: this was a control
asserted from the shape of a pipeline rather than run through it, which is the exact
error class the Z-gates exist to catch, committed while documenting a gate whose
subject is that error class.

## Pass 4 — CodeQL, on the PR

One high-severity alert, `py/incomplete-url-substring-sanitization`, against the
committed harness: `z6.py` classified observed requests with `"unpkg.com" in url`.

**Fixed rather than dismissed, because the alert was right about the gate.** The
harness is a probe, not a sanitiser, so nothing was exploitable — but Z6's central
assertion is *"no request to unpkg was attempted"*, and a substring test makes that
assertion answerable by an unrelated query string. Verified after switching to a
parsed-host comparison:

| URL | substring check | parsed host | correct |
|---|---|---|---|
| `https://unpkg.com/mermaid@11/…` | match | match | match |
| `https://cdn.unpkg.com/x.js` | match | match | match |
| `https://evil.example/?x=unpkg.com` | **match** | no match | no match |
| `https://unpkg.com.evil.example/x.js` | **match** | no match | no match |

The last row is the one that matters: a look-alike host would have been counted as a
legitimate unpkg fetch. The positive control still detects both real unpkg requests
and the gate run still reports zero, so the fix is stricter without weakening
detection. `file://` is now classified by scheme rather than by string prefix for the
same reason.

**This is the third time in one change that a check was weaker than the claim it
supported** — after the `attr_list` allowlist and the D46 table-row grep. The pattern
is consistent enough to be worth naming: every one of them tested a *proxy* for the
property rather than the property.
