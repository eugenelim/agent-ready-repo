## Outcome

Repository maintainers get direct observed evidence about efficient agent loops:
which delivery facts should stay fixed, which construction decisions should
evolve, whether separate specifications and plans help, where stronger models
add value, and which review policy reduces churn without hiding defects.

The managed runtime cannot enforce candidate-code confinement, so the amended
study makes no causal or build-performance claim. It runs real provider
subjects only over non-secret document packets and reports every result as
non-inferential.

The durable result is a self-contained research report and reproducible
workbench. It remains useful after this delivery spec and plan are pruned.

The final amendment narrows the effectiveness question to real delivery work.
It treats the synthetic cross-model extension as a methodological negative
result and measures whether review closes durable risk at proportionate cost
without creating a prose-repair loop. It does not rank models or require a
zero-finding verdict.

## Run sets

### Run 0 — calibration and recovery

Two disposable document tasks cross four core artifact forms for eight
non-inferential construction responses. The gate proves assignment
randomization, treatment rendering, prompt/response receipts, static grading,
tool-use deviation capture, and terminal accounting. It launches no candidate
subprocess and does not repeat the impossible secure-confinement or
provider-token gate.

Run 0a is a completed failed calibration and stays immutable. Its eight starts
used compact controller messages instead of the frozen prompt bytes, so every
rendering receipt failed and two responses also failed the frozen schema. It is
protocol evidence only and is never pooled with treatment results.

Run 0b is the one owner-approved recovery. It repeats the same two-by-four
calibration with eight fresh cold workers and fresh study ordinals 9–16. Each
worker receives the exact bytes of a newly frozen Run 0b prompt, including the
complete response schema, and is launched with the declared requested model
route. The controller stores the intended prompt digest and actual-dispatch
digest before launch and requires byte equality. It does not repair or reuse a
Run 0a response. A Run 0b parse, schema, alias, atom, privacy, deviation,
receipt, or accounting failure closes every later collection without another
replacement calibration.

Before Run 0 and each inferential release, the controller captures the active
managed permission profile and exposed tool surface. Inferential release fails
closed before launch unless protected credential/configuration paths are denied
by platform policy and web, network, delegation, approval escalation, and
external-messaging tools are absent or denied. A run whose tool surface fails
that gate may be retained only as unreleased, non-inferential,
`non-secret-bearing-input-only` evidence; observing compliant worker behavior
after launch cannot upgrade it. Candidate-root-only read authority is not
available and is not a release predicate or safety claim. Any observed
out-of-candidate access is a terminal protocol deviation; possible unobserved
access remains a permanent validity limitation.

The same release record covers controller-observable credential-bearing
environment variables, service-auth or launch tokens, runtime sockets,
credential brokers, OS keyring access, and protected configuration. No value is
read or copied during that check. A visible or worker-accessible credential
surface stops release. If the runtime cannot make a surface observable, the
assignment is labelled `non-secret-bearing-input-only`: no secret is supplied
in its prompt, candidate, task package, report template, or controller
environment overlay, but runtime credential isolation is explicitly
unverified.

### Run 1 — pre-execute review policy

Six tasks × three policies × three cold replications produce 54 matched review
trajectories. Each trajectory has at most three review starts over an identical
frozen three-revision artifact sequence with an independently adjudicated
defect registry.

- full replay on every revision;
- broad first review, then delta plus affected-invariant review;
- broad first review, then one cold closure review over the final artifact.

Reviewers do not edit subjects. This isolates review aperture from repair
quality. The primary outcomes are known-defect recall, precision, unique
sustained findings, repeated or reopened findings, rounds, and churn prose.

### Runs 2–5 — shared-control document-construction panel

Six tasks × three replications form 18 blocks. Each block has one initial plan
author and five construction-response arms, for 18 plan-author starts and 90
document trajectories. A response contains only a decision record, proposed
change manifest, acceptance mapping, self-audit, and optional plan amendment.

| Run | Arm compared with the shared baseline | Objective |
| --- | --- | --- |
| 2 | Frozen thin plan versus controlled-evolving thin plan | Isolate amendment authority while the semantic outcome remains fixed. |
| 3 | Separate spec/plan versus one unified contract | Isolate artifact packaging with equal fact atoms, order, visibility, prompt, model request, limits, and amendment policy. |
| 4 | Thin decision/check plan versus narrative-expanded plan | Isolate added rationale, examples, and sequencing prose; add no obligations, decisions, or checks. |
| 5 | Cold builder handoff versus one worker planning and building | Measure continuity while keeping task, model request, and artifact policy fixed. |

The shared baseline is a separate stable-outcome spec plus a thin,
controlled-evolving plan handed to a cold builder. Every amendment records its
trigger evidence, changed construction decision, affected tasks and checks,
and the unchanged outcome digest. A contradiction to the outcome stops every
arm; evolution never authorizes scope change.

### Run 6 — requested model allocation for document work

Four frozen tasks — two medium, two complex, two pre-build, and two
reconstructed — cross requested planner and builder routes in a 2×2 design:
`gpt-5.6-luna` and `gpt-5.6-sol`. Three replications produce 48
planner-constructor trajectories and 96 starts. Results describe requested
routing and document quality only unless the runtime exposes served identity
independently; they do not estimate build performance.

### Run 7 — document-construction review loop policy

Twelve construction responses are selected by a frozen, treatment-blind stratification
rule and copied before review assignment. Each copy enters one of the three Run
1 policies. The 36 trajectories permit at most three review starts and two
repair starts each. The same repair model request, repair brief, and opportunity
count apply across policies. Static hidden-registry grading runs after every
document repair. Constructor and repairer self-audits are captured before fresh
review; no repair executes or edits candidate code.

The primary outcomes are residual severe defects, net new sustained findings,
repair benefit, repair-origin defects, convergence, and reviewer churn.

### T13 methodological closeout

T13 ran 95 terminal starts and seven review rounds. Its apparatus repeatedly
reproduced the defect families it was meant to detect: tautological checks,
self-matching taxonomy tests, shape checks presented as property checks,
fail-open carry behavior, stale byte bindings, and grader decisions on
judgment surfaces. The final controller retired seven self-certifying modules
and retained their history instead of attempting an eighth repair round.

This is a useful negative result about experimental method. It does not answer
whether the work-loop is effective in natural delivery work, whether closure
review is safer than full replay in the wild, or whether one model route is
better than another. The Sonnet, Opus, and synthetic validation blocks are
cancelled. Their reserved ceiling grants no launch authority.

### Natural-work effectiveness study

The replacement study starts from the repository's existing natural evidence:
four independently normalized Tier-A review histories, two aggregate cases,
the occasioning 15-round Claude Code loop, and the repository-wide transcript,
pull-request, spec/plan, and acceptance-criterion survey. T14 recodes these
histories against one frozen event definition before any prospective case is
eligible.

T15 observes consecutive eligible work-loop cases rather than selected
synthetic tasks. The normal loop runs one broad cold adversarial review plus
only triggered specialist reviews, adjudicates blocking findings, repairs
sustained blockers, and performs one focused closure review limited to the
sustained findings, changed bytes, affected dependencies, and repair-origin
regressions. It stops when blocking consequences are closed and records
advisory residue without requiring `Clean`.

One independent cold reviewer then performs a full-document **shadow audit**
over the exact stopped revision. The shadow audit measures possible escape; it
does not itself reopen advisory prose. A shadow blocker counts as an escape
only after independent adjudication sustains it against a stable requirement,
an executable failure, a protected risk, or genuinely new external evidence.

The study does not prescribe a model route. It records author, reviewer,
repairer, adjudicator, and shadow-auditor requested models and resolved models
when observable. Historical cases with missing model identity remain eligible
for lineage and churn measures but not model comparisons.

## Measurement plan

Effectiveness is durable delivery risk removed per review cost, with a penalty
for defects and churn introduced by the loop. No scalar combines those terms.
The report presents this scorecard for each case and in aggregate:

- durable blocker closure rate;
- protected-defect escape rate from the independently adjudicated shadow audit;
- unique durable blockers found per review start;
- repair-origin blocker rate;
- accepted-surface reopen rate;
- same-family recurrence after repair;
- same-revision reviewer/adjudicator disagreement;
- appeal reversal and indeterminate rates;
- prose-churn event rate and prose-churn events per review start;
- observable reviewer, adjudicator, and repair actions, tokens, and wall-clock
  time attributable to prose-churn events, both as totals and as a share of
  observed review-loop cost;
- observable input/output tokens and wall-clock time per durable blocker closed;
- repair and adjudication actions per durable blocker closed; and
- the share of findings that changed accepted scope, implementation, tests, or
  a protected control.

A **durable blocker** is a finding independently sustained against the stable
contract or direct evidence whose closure changes an accepted requirement,
implementation, executable test, or protected control. A **prose churn event**
is a blocking finding against unchanged, previously accepted text that brings
no new requirement, executable failure, protected risk, or external evidence.
A **protected-defect escape** is a shadow-audit blocker that independent
adjudication sustains on one of those grounds after the normal loop stopped.

The prose-churn numerator is every blocking finding that meets that definition;
the denominator is every blocking finding emitted after the first accepted
revision in the same cases. Report the fraction, raw numerator and denominator,
and events per review start. Attribute review, adjudication, and repair cost to
an event only from retained role/action lineage; otherwise mark that cost
unavailable instead of estimating it.

Wall clock, tokens, tool traces, resolved model, session identity, and human
intervention are recorded only when directly observable and are never
estimated. Missing historical telemetry stays unavailable. Raw finding count,
report length, `Clean`, and seeded-defect recall are descriptive only; none is
a quality denominator or completion gate.

The consecutive eligible case is the unit of generalization. Retrospective and
prospective results stay separate. Report case-level values, medians and ranges,
missingness, and every protected escape. Do not treat review starts as
independent samples or claim causality from this observational cohort.

## Document isolation, grading, and contamination

- Generate each subject from a frozen non-secret document packet. Do not give
  experimental subjects a repository checkout, candidate source tree, shell
  command, executable attachment, or hidden registry.
- Keep reference responses, defect registries, sibling outputs, treatment
  labels, and scoring keys in controller-only documents not included in the
  subject prompt.
- Instruct workers not to inspect the source repository, historical commits,
  sibling roots, hidden material, credentials, browser profiles, or protected
  configuration; prompts request no web, delegation, escalation, tool use, or
  external messaging.
- Freeze prompt and response digests. Validate output as bounded text or strict
  JSON, then grade it with controller-side static comparisons only. Never
  execute, import, evaluate, or shell-expand agent output.
- Scan prompts and reports for reference identifiers, hidden paths,
  reference-only markers, and disclosed tool use. Any tool-use or
  out-of-packet access is a terminal protocol deviation and excluded from the
  matched comparison; a failed cell is never retried.
- For every controller or model-derived document path, reject symlinks,
  reparse points, junctions, multiple hard links, special files, absolute or
  traversing members, path loops, and identity changes between checks and open.
  Canonicalize and verify containment under the declared document root before
  a parser, static grader, or report sink consumes the bytes.

These controls reduce accidental leakage. They do not prove non-access.

## Agent Rules

### Always do

- Reserve a unique collaboration-study ordinal before every agent start and
  end every reservation in one terminal record.
- Freeze blocked randomization by task and replication before Run 0; balance
  arm launch position and keep holdouts unreleased.
- Keep treatment labels blind in worker and scorer inputs where the treatment
  does not inherently reveal its form.
- Treat agent output as untrusted data and validate bounded strict schemas,
  paths, digests, phase order, and terminal receipts before grading or analysis.
- Frame every worker-visible document or source body as attributed untrusted
  data, and keep run, tool, path, scoring, hidden-material, and schema authority
  outside that frame.
- Preserve the legacy failed blocks and retrospective study as separate evidence.
- Report missing telemetry, runtime deviations, contamination, and exclusions.
- Keep retrospective, T13 synthetic, and prospective natural-work evidence in
  separate classes.
- Admit prospective cases consecutively under the frozen rule and bind the
  stopped revision before its shadow audit.

### Ask first

- Change an outcome, comparison, task split, scoring rule, released manifest,
  prospective inclusion rule, protected-defect class, stop rule, model policy,
  decision threshold, or process budget.
- Enable worker network use, delegation, external messaging, or access to
  protected configuration.
- Turn a research result into production work-loop policy.

### Never do

- Give a worker the reference patch, hidden tests, grading command, another
  cell’s output, or prior treatment result.
- Inspect credentials, browser profiles, protected configuration, or personal
  data as part of calibration or diagnosis.
- Execute, import, or evaluate agent-authored commands, paths, or code.
- Drop failures, retry until success, alter scoring after outcomes, or pool the
  collaboration block with a failed provider block.
- Treat a shadow audit's advisory prose or unadjudicated judgment as a reopened
  blocker.
- Merge any candidate implementation into the product tree.

## Testing Strategy
