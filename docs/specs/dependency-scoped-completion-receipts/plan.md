## Approach

Four layers, dependency-ordered, each leaving the repository working: the
published shape, then the consumer that reads it, then the producer that must
not emit what the consumer would refuse, then the records.

The consumer lands after the schema because the schema is what an adopter
writes by hand and what the engine's parser must agree with; the producer lands
after the consumer because tightening `plan_completion_receipt` rewrites two
shipped Wave 4 fixtures, and doing that before the consumer exists would leave
a window where the fixtures assert a grammar nothing reads.

## Design (LLD)

### Design decisions

The receipt is an optional object on `$defs/localNeed` rather than a third need
variant, so `Dependency.type` keeps exactly two values and no engine branch on
`local` versus `cross-repo` is disturbed.

`invalid_receipt` is reused for a malformed local receipt rather than a new
finding code. Its documented sentence is broadened from "Cross-repository
receipt" to cover both carriers, keeping one code for one meaning — the receipt
you were given is not usable — and adding no entry to the finding-code surface.

### Data & schema

`receipt` is an object with `additionalProperties: false` and all four
properties required when the object is present. `delivery_id`,
`completion_event`, and `evidence_ref` restate the lifecycle record's grammars
as values; AC3's test is what keeps the two copies equal, because JSON Schema
`$ref` across contract files would couple two independently versioned
`contract_version` documents.

### Interfaces & contracts

`contracts/jsonschema/workspace-entry.schema.json` gains the `receipt` object
and an `x-spec` entry naming this spec directory.

### Behavior & rules

In `_dependency_is_satisfied`, the new branch sits after the
`structurally_blocked_paths` guard and after the cooled-dependency return, in
the arm where `matches` is empty. It runs only when the probe's metadata reports
the artifact absent — the point that returns `missing_dependency` today.

### Failure, edge cases & resilience

A receipt whose target artifact still exists is ignored rather than refused:
closeout writes the receipt and a later wave prunes the file, so both existing
at once is the ordinary transitional state, not a contradiction.

## Tasks

### T1: Publish the receipt shape and pin its grammars

**Depends on:** none

**Touches:** contracts/jsonschema/workspace-entry.schema.json, tests/roster/test_dependency_scoped_completion_receipts.py

**Tests:** TDD. Verifies AC1, AC2, AC3.
- A `local` need with no `receipt` validates, and one with a four-key `receipt` validates.
- A `receipt` missing any one of the four keys fails; a `receipt` with a fifth key fails.
- `outcome` accepts each of the three vocabulary values and rejects `Cooling`, `Retained`, `Retired`, `ExternalAdvisory`, and the empty string.
- Cross-file equality: the receipt's three grammars equal the values read from `delivery-lifecycle-record.schema.json` at the three named JSON paths.
- Red contract-surface stub (`stub: true`): the cross-file equality assertion, which fails against the unmodified schema because no `receipt` object exists to compare.

**Approach:**
- Add `receipt` to `$defs/localNeed` with `additionalProperties: false` and the four required properties.
- Add this spec directory to the schema's `x-spec` array.

**Done when:** the new suite's AC1–AC3 assertions are green, and the mutation in the table below reddens AC3.

## Mutation proofs

Every guard names the mutation that must redden it. Observed results are
recorded in [`notes/mutation-proofs.md`](notes/mutation-proofs.md), never here.

| Criterion | Invariant | Mutation | Expected failure |
| --- | --- | --- | --- |
| AC3 | The receipt's grammars equal the lifecycle record's | Change one character of the receipt's `evidence_ref` pattern in `workspace-entry.schema.json` | The cross-file equality assertion fails on `evidence_ref` |
| AC4 | A valid completed receipt satisfies an absent dependency | Delete the satisfaction branch from `_dependency_is_satisfied` | AC4's fixture reports `missing_dependency` instead of no finding |
| AC5 | A surviving membership wins before the receipt is read | Move the satisfaction branch above the `structurally_blocked_paths` guard | AC5's fixture reports no finding instead of `unsatisfied_dependency` |
| AC6 | A non-landed outcome still refuses | Accept any vocabulary value as satisfying | AC6's `abandoned` and `superseded` fixtures report no finding |
| AC7 | A malformed receipt refuses | Drop the extra-key check from the receipt parser | AC7's fifth-key fixture reports no finding instead of `invalid_receipt` |
| AC8 | A present artifact ignores the receipt | Let the satisfaction branch run before the artifact-existence check | AC8's non-terminal fixture reports no finding instead of `unsatisfied_dependency` |
| AC9 | The two receipt paths stay distinct | Route a local `receipt` through `_cross_repo_receipt_satisfied` | AC4's fixture reports `invalid_receipt` |
| AC10 | The producer applies the same grammars | Remove the grammar checks from `plan_completion_receipt` | AC10's three invalid calls return `receipt-write-confirmation-required` |

## Rollout

No migration and no deployed data: no receipt exists anywhere in the repository
today, so the tightened producer validation cannot reject a persisted record.
The schema change is additive — every existing `local` need remains valid.

## Risks

- **The two grammar copies drift.** Mitigated by AC3 reading the lifecycle
  record at test time rather than restating its values.
- **The consumer has no producer until Wave 7c prunes anything.** Accepted: a
  maintainer can write a receipt by hand today, and Wave 7c's fixtures need this
  contract to exist before they can be real rather than hypothetical.
- **`close-work-extraction-and-immediate-disposition/plan.md` may be frozen.**
  T3 confirms before editing and surfaces rather than working around it.
