## Objective

A skill installed straight from a repository has a route to a later revision of itself, so long as that revision does not widen its declared capability surface; one that does is refused and the adopter reinstalls, until `direct-lifecycle-capability-reconsent` lands. `upgrade --skill <name>` re-resolves the skill's recorded source and path, re-runs the shared admissibility gate, previews the file plan, and replaces the projection. When the recorded source names a moving ref, re-resolution finds whatever that ref points at now; when it names a commit, `--source` supplies the revision to move to.

An install that names a different revision of an already-installed skill stops and says so, because a revision is a version of an identity rather than a new one.

## Scope

This spec owns identity and the upgrade route. Nine areas are deferred; `## Follow-ons` names each with its owner.

Capability re-consent is deferred rather than dropped, and its absence bounds this spec: AC7 refuses an upgrade that widens a capability axis, with no acceptance flag. That refusal is the conservative half of the deferred criterion, not a substitute for it.

Two further bounds are stated here because the discovery intent's outcome is wider than this slice:

- The intent's steerable input is the share of directly installed skills reachable by an update path **that names what changed**. This spec moves the reachability half only. AC8 prints the full declared surface and AC2 previews the file plan, but no criterion here renders an old-to-new capability delta; that half is `direct-lifecycle-capability-reconsent`, and the receipt that would carry it is `direct-lifecycle-receipts`.
- A row whose `ref_kind` is `sha` or `abbreviated-sha` moves only through AC3's `--source`, for which `list-installed --format json` supplies the repository element — F5 measures that it emits the row's stored source, carrying the old ref — while the adopter supplies the new revision themselves. No per-skill surface renders it: `show <direct-row>` exits 1 and the table's SOURCE column is `direct-lifecycle-display`'s. So the intent's "without remembering the source string" holds for `ref` rows, and for pinned ones holds only via that JSON. No fact row measures the pinned share, so the size of that gap is unmeasured.

## Assumptions

- RFC-0098 D4 mandates `upgrade --skill <name>` without `--pack`: it re-resolves a manifestless skill's recorded source and path, re-runs admissibility, previews the file plan, and replaces it. No erratum retires it (read, 2026-09-01).
- RFC-0098 D4 defines a direct identity for collision as `(source-kind, canonical source, source-path)` and states revision and digest "describe a version of that identity and may change only through upgrade; they do not make a colliding install a new source" (read, 2026-09-01).
- RFC-0098 D6 mandates repository, user, **and local** scope for standalone skill upgrade. This spec delivers the first two and leaves `--scope local` at the exit 2 F5 measures, because widening `cli.py`'s choice set would move `upgrade --pack P --scope local` off an exit-2 clause D6 calls unchanged. That is a knowing partial delivery of D6, owned by `direct-lifecycle-local-scope`, and is one of three places this spec does not fully conform to a decision its header cites. The second is D6 rule 7's receipt, deferred to `direct-lifecycle-receipts`, of which AC1 keeps only the no-update line. The third is D6's requirement that the parser report the `--skill` distinction in help, deferred to `direct-lifecycle-author-documentation`.
- The parent spec's AC3 records the resolved 40-hex SHA as `source-revision` and pins branches and tags to it, while the stored `source` keeps the requested string (read, 2026-09-01). What re-resolution then reaches per `ref_kind` is F1, and is not restated here.
- Every other assumption this spec once carried in prose is now a row in `## Grounded facts` and is stated only there: today's `upgrade` reachability and exits are F4 and F5, the shipped collision comparison is F6, and the capability axes and their absences are F2.

### F1 — A stored ref has three kinds, and two of them are fixed points

`direct_source_acquisition.py` classifies `ref_kind` as exactly `"sha"`, `"abbreviated-sha"`, or `"ref"`: 40 hex is `sha`, 7–39 hex is `abbreviated-sha`, hex of any other length is refused outright, and everything else is `ref`. A defaulted ref is refused before classification, so a `ref` row is a **tag or a named non-default branch**, never a bare default. A tag and a branch are both `ref` and are **indistinguishable in the stored string** — `_REF_RE` admits `[A-Za-z0-9._/-]{1,255}` for both. A direct source names exactly one owner and one repository and carries **no path component**, and `.git` is stripped from the repository before the request is built, so two spellings of one repository fetch identical bytes.

| `ref_kind` | Re-resolving reaches | Decidable from the stored string |
| --- | --- | --- |
| `sha` | the same commit, or a refusal | yes — 40 hex |
| `abbreviated-sha` | a commit whose SHA carries that prefix, or a refusal. `acquisition` verifies `candidate.startswith(ref)` only, so a prefix collision is not detected | yes — 7–39 hex |
| `ref` (branch or tag) | whatever the ref points at now | yes as a class; branch-vs-tag is **not** |

### F2 — Each capability axis has a named absence, and absence is the widest state

`direct_source_state.py`: `allowed_tools` is `frozenset[str] | None`, and `_tool_display` renders `None` as the single `UNDECLARED_TOOLS` member. `boundaries` is a `frozenset[str]`. `_normalised_credentialed`'s range is given in the table below and is **not** closed over three tokens.

The **producing** path collapses a distinction the comparing path preserves: `direct_install._normalised_allowed_tools` returns `[]` for an absent `allowed-tools`, for `[]`, and for `""` alike, and `_render_tools([])` prints `undeclared (unrestricted)` for all three. So the consent surface cannot distinguish "no declaration" from "an empty declaration", and a widening predicate that keys on `None` alone never fires for a publisher who empties the list instead of removing it. AC7's transition is therefore written over *stops restricting*, not over `None`.

| Axis | Type | Absence | Widening transitions |
| --- | --- | --- | --- |
| `allowed-tools` | `frozenset[str] \| None` | `None`, rendered `undeclared (unrestricted)` | a member is added; **or the declaration stops restricting** — becoming absent, empty, or `None` — which grants everything |
| `metadata.boundaries` | `frozenset[str]` | empty set | **a constraint is added.** `compare_capabilities` computes `widened = new - old`: a boundary names a capability the skill *crosses*, so acquiring one widens and dropping one narrows |
| `metadata.credentialed` | **not a closed set** — `_normalised_credentialed` returns `"undeclared"` for `None`, `"true"`/`"false"` for a bool, and `str(value)` for anything else | `"undeclared"` | any transition to a value that is not `"false"` or `"undeclared"`. The direct route reads this field from publisher frontmatter unvalidated, so `credentialed: "yes"` normalises to `"yes"` |

`compare_capabilities` returns `CapabilityDelta((), unknown=True)` when the prior surface is unreadable — an **empty** difference tuple. It also reports a **strictly larger** set than these three axes: it appends `SKILL.md digest changed`, `payload digest changed`, `payload added`, `payload removed`, `skills added`, and `skills removed`, and `requires_reconsent` is `unknown or bool(differences)`. Since AC6 defines an available update as exactly a changed digest, a predicate keyed on `requires_reconsent` refuses every upgrade this spec exists to perform. Both are invariants AC7 rests on, and AC7 therefore names its own predicate over the three axes.

One clause of this row is a baseline, not an invariant: `differences` are today rendered strings rather than typed per-axis outcomes. **Changed by T6**, which is why T1 does not pin it.

### F3 — The state row's fields, and which an upgrade must touch

`config.PackState` carries seventeen fields: `installed_version`, `source`, `install_route`, `scope`, `primitives`, `files`, `primitive_versions`, `adapter`, `target_file`, `hook_wiring_owned`, `user_root`, `artifact_uri`, `archive_sha256`, `source_revision`, `source_kind`, `source_path`, and `source_digest`. `files` is the ownership map `State.owners_of` reads, and it is keyed per `(name, adapter)` row. `_data/adapter.toml` declares `shared-prefixes` — `.agents/skills/` for `codex`, `cursor`, `gemini`, and `copilot`, and `.kiro/skills/` for `kiro-ide` and `kiro-cli` — and two direct rows owning one file is reachable in one way and not another. Within **one** state file the guard holds: installing a skill for a second adapter in the same group exits 1 with `CAT-D009`, "Overwriting would leave two rows claiming one path with different contents" (measured). But `_refuse_foreign_owner` resolves a single state file for the scope it is given, so it cannot see another scope's rows — and a user-scope install and a repo-scope install anchored to the **same root** both exit 0, writing two state files (`.agentbundle-state.toml` and `.agentbundle/state.toml`) whose rows own one file at one inode (measured). `uninstall` already handles that shape by keeping any file another row still owns.

Rows for adapters in *different* prefix groups are reachable and ordinary too: `claude-code`, `codex`, and `kiro` coexist for one name, which is the state AC1's `--adapter` disambiguation exists for. `direct_source_digest` emits the current digest prefix unconditionally, so a re-resolved digest always carries a prefix this build knows. Every direct row is written with `installed_version = MANIFESTLESS_VERSION_SENTINEL`, and `list_installed` depends on that sentinel never becoming a real version.

The direct install path writes **nine** of the seventeen: `installed_version`, `source`, `scope`, `adapter`, `source_revision`, `source_kind`, `source_path`, `source_digest`, and `files`. It passes no value for `archive_sha256`, `artifact_uri`, `install_route`, `primitives`, `primitive_versions`, `target_file`, `hook_wiring_owned`, or `user_root`, so each takes its dataclass default. **The layer matters:** those defaults are serialised, so a persisted direct row does contain `install-route = "cli"`, `user-root = "~/.agentbundle"`, and `primitives = []` (measured). The invariant is therefore that an upgrade leaves each of the eight at the value a fresh install of the same source produces — not that the state file omits them.

### F4 — `upgrade` today cannot reach a direct row

`--skill` is **not** a free flag. `cli.py` already declares it in a five-way mutually exclusive group with `--agent`, `--hook`, `--seed`, and `--command`, and `commands/upgrade.py` uses `--pack P --skill S` to upgrade one primitive inside a catalogue pack, writing `primitive_versions[<ptype>][<name>]`. RFC-0098 D6 requires that meaning to be retained and ambiguous combinations rejected. **Changed by T3.**

`commands/upgrade.py` contains **zero** references to `source_kind`. It resolves a catalogue URI and reads its target from the catalogue's `pack.toml`, gating only on `state.has_pack(name)`. Its bulk path iterates `state.packs.items()` with no filter, so `--all` already reaches direct rows and calls `canonicalize_source` on their stored source. **Changed by T8.**

### F6 — Where a stored source is transformed today

`direct_install.py` `stored_source_for` stores a repo-scope in-repository source **relative to the repository root**; a `git+https` source and an out-of-repository path are stored verbatim. `commands/upgrade.py` calls `canonicalize_source` on a stored source and falls back to the default-source chain when the stored value is `None` or the legacy string literal `"agent-ready-repo"`. That fallback is the branch AC5 forbids a direct row from taking, so it is a baseline this spec changes — **changed by T5**, and not pinned by T1. The rest of this row is invariant. That literal is the sentinel AC5 names; it is unrelated to `MANIFESTLESS_VERSION_SENTINEL`, which is an `installed_version` value.

`canonicalize_source` resolves a schemeless value with `Path(value).resolve()`, which anchors it to the **process working directory**: `canonicalize_source("vendor")` returns `<cwd>/vendor`. That is the baseline AC5 changes — **changed by T5** — and the reason AC5 re-establishes the root from the state file that owns the row. The rest of this row is invariant.

Because a repo-scope source is stored relative, the stored string is not the string the parent spec's AC3 grammar admitted. AC5 applies that grammar to the form the request is built from — the absolute `git+https` URL as stored, or the relative path re-anchored to the repository root that owns the state file.

### F7 — What `--dry-run` ships as, and what its plan renderer shows

`cli.py` declares `--dry-run` on `upgrade` as "Preview the per-file plan (action + tier + target path) without writing anything". Its renderer in `commands/upgrade.py` iterates `sorted(work_projection)` — the **incoming** projection set — and prints one line per entry. A file the row owns that the new revision does not contain appears nowhere in that output, so removals are structurally invisible to the shipped renderer. **Changed by T3b**, which AC2 requires to enumerate removals.

The remote gate is `not args.yes and not args.dry_run` with **no terminal test**, so it fires interactively too: a remote source always requires `--yes`, and `--dry-run` is exempt.  `direct_install.py` exempts `--dry-run` from the remote `--yes` requirement, on the stated grounds that it is the only way to read the admissibility summary for a remote source before consenting. The remote refusal without `--yes` happens **before acquisition**, and the code comments that the message must not claim a summary it has not produced. Both are invariants AC1 and AC8 rest on, and they are the only clauses of this row T1 pins; the renderer clause above is the baseline T3b breaks.

### F8 — The terminating remediation, measured

`uninstall --pack <name> --root <root> --scope repo --yes` on an installed manifestless row exits **0**, prints `uninstall: 1 removed, 0 kept`, and removes the state row and every file that row owns. `uninstall.py` carries no `source_kind` branch, so it reaches a direct row by name like any other. The install receipt prints `agentbundle uninstall --pack <name> --yes` as the row's removal form — the same verb and selector, without the `--root`/`--scope` a non-default invocation needs.

**Two measured limits.** First, `uninstall` keeps an adopter-edited owned file rather than removing it: with the projected `SKILL.md` locally edited, the same command exits 0, prints `uninstall: keeping adopter-edited file: …` and `uninstall: 0 removed, 1 kept`, deletes the row, and leaves the file — after which a fresh install exits 1 with `CAT-D009 … Move or delete the existing file first`. So remove-then-install does not terminate on its own when a projected file has been edited. Second, both `upgrade` and `uninstall` declare `--root` with a default of `.`, so a printed command omitting `--root` is accepted only from the root the row was installed against: run from a subdirectory it reports `pack '<name>' not installed` and exits 1. A second measured trap: on a row installed for more than one adapter, `uninstall --pack <name> --yes` without `--adapter` exits 1 with `installed for multiple adapters at repo scope; pass --adapter to pick one` — and that message renders each row's version as `0.0.0`, a fourth surface reaching the sentinel the parent spec's AC26 first sentence forbids. `uninstall`'s surfaces are `direct-lifecycle-uninstall-skill`'s; AC10 owns only `upgrade`'s two.

**The clean-row claim holds only for files the row still owns.** Measured: install a skill carrying `SKILL.md` and `references/doomed.md`; drop `doomed.md` upstream; reinstall the byte-identical source. The reinstall exits 0 and drops `doomed.md` from `files`, but leaves it on disk — the install path has no deletion pass, its only `rmtree` being the temporary acquisition tree. A subsequent `uninstall --pack … --yes` then exits 0 and **leaves `references/doomed.md` behind**, because uninstall removes what the row owns and the row no longer owns it. So a reinstall across a revision that drops a file strands publisher bytes that no row owns. Measured against the three commands that might surface it, none does: neither `install`, nor `list-installed`, nor `list-installed --check-drift` mentions the orphaned file. The parent spec's AC28 states unqualified that install and list surface unowned projections, and it is ticked. This spec reads that clause as scoped to the interrupted-install post-condition its criterion title and preceding sentence establish, which is also mechanically coherent — install surfaces an unowned projection only where it collides with a destination it is about to write, and a completed-run residual is by construction a path the new revision no longer names. That reading is an interpretation, not a measurement, and it is the scope owner's to confirm; under the wider reading the measurement above is a defect against AC28 rather than a residual this spec routes. That residual belongs to the install route and predates this spec; AC12 gives the upgrade route the deletion pass that avoids it, and AC7 routes around it.

This is what makes a remediation terminate for a row whose `ref_kind` is `sha` or `abbreviated-sha`: re-resolving the stored source reaches the same commit by F1, so a reinstall cannot move such a row, and `uninstall --skill` does not exist (F5). Remove-then-install is therefore the only sequence that both moves a pinned row and takes install's full consent surface.

### F9 — The prior capability surface has no producer

`compare_capabilities` and `Capabilities` have **zero production callers**: both are referenced only from `packages/agentbundle/tests/unit/test_direct_upgrade.py`. The one production reader of `allowed-tools`, `direct_install._normalised_allowed_tools`, reads the **candidate source**, never an installed projection. The parent spec's AC12 carries a ticked clause requiring old capability data to be re-derived from the projection; no code does it.

So the delta AC7 refuses on is not something the upgrade route reads — it is something this spec's implementation must first produce, by parsing the projected `SKILL.md` frontmatter back into a `Capabilities`. That producer is new code, not a call into existing code. Its input is simple: measured across all eight adapters, a skill's projected `SKILL.md` is **byte-identical to the source** — `allowed-tools`, `metadata.boundaries`, and `metadata.credentialed` all survive verbatim, and no adapter rewrites skill frontmatter. So the producer parses one format, not eight: `parse_bounded_metadata` over the projected file returns `allowed-tools`, `metadata.boundaries`, and `metadata.credentialed` directly (measured). It returns the **raw** value, so `allowed-tools: Read, Bash` comes back as a string and `["Read","Bash"]` as a list: the comparison runs over `_normalised_allowed_tools`' output, not the parse's, or a publisher who only respells the declaration reads as a difference.

`Capabilities` carries six fields, not three — `skill_digest`, `skill_identities`, and `payload_digests` besides the axes — and those three exist to produce exactly the differences F2 records as the ones AC7 must ignore. Constructing a full `Capabilities` from a projection would mean re-deriving digests in order to discard their differences, so the producer this spec needs yields **the three axes only**. `compare_capabilities` keeps its wider surface for `direct-lifecycle-capability-reconsent`, which does act on the digests. **Built by T6.**

## Boundaries

### Always do

- Compare the three capability axes directly, and do not construct a full `Capabilities` to reach them: F9 measures that its other three fields would have to be re-derived from the projection only to produce differences AC7 must ignore. `compare_capabilities` stays as shipped for the deferred re-consent slice.
- Route `upgrade --skill` through the same preflight, projection, and ownership paths install uses; RFC-0098 D6 makes these thin selectors, not a second lifecycle engine.
- Cite the owning document for a rule this spec depends on: RFC-0098 by decision id, the parent spec by path and criterion number.

### Ask first

- Merging without the security evidence AC4 and AC1 require; the boundary is capability consent, and the parent carried its own evidence artifact for the same reason.

- Registering a `DIRECT_CODES` member beyond those the criteria already mandate. The members AC1, AC2, AC3, AC4, AC5, AC6, AC7, AC8, AC10, and AC12 require are pre-authorised by the approval of those criteria. **AC12 was added to that list on 2026-09-03 by the scope owner**, in response to a sustained secure-design finding that its repaired failure handling mandated a member the gate did not cover. It carries exactly **two**, under this bullet's own distinct-refusal rule: one for a failed `unlink` of an owned file, whose remediation clears the obstruction on that file, and one for a failed prune of an emptied directory, whose remediation clears that directory — two different targets and two different printed remediations, so one shared member would be the defect this gate exists to prevent. AC12's ownership-determination-cannot-complete branch takes **no** member, because it does not refuse. Both members are `CAT-D020` and `CAT-D021`, the next free ordinals above the nineteen `CAT-D001`–`CAT-D019` registered today. Every member listed here is pre-authorised by the approval of its criterion, and each distinct refusal listed there is a distinct member — a shared member for two refusals with different remediations is the defect the table exists to prevent; this gate covers any member past them. Either way the published table at `guides/catalogue-curation/reference/direct-install-diagnostics.md` is live and `tools/lint-direct-code-table.py` passes today, so every new member lands with its table row in the same change; the deferred documentation slice owns the author-facing pages, not this table.
- Any change to `list-installed` output, which is `direct-lifecycle-display`'s subject.
- Contracting what a successful `upgrade --skill` prints as a receipt, which is `direct-lifecycle-receipts`' subject; this spec contracts the pre-write consent surface only.
- Admitting `--scope local` on any direct route, which is `direct-lifecycle-local-scope`'s subject.

### Never do

- Add an unattended discovery mechanism: no background probe, no status fetch, no registry, and no outbound request outside a user-invoked `upgrade`.
- Add a runtime dependency, a new top-level directory, or a new transport.
- Admit an upgrade that AC7 refuses, or add an acceptance flag while `direct-lifecycle-capability-reconsent` is open.
- Write previously accepted capability values into the state row as a new schema field; RFC-0098 D4's state schema 0.5 stays as shipped.

## Testing Strategy

One entry per criterion: its verification mode, and the boundary the test must run at. The fixtures and the killing case for each are `plan.md`'s, and are stated only there.

- **AC1** — TDD, unit. The accepted and rejected invocation set is a decision over parsed arguments plus a loaded state file.
- **AC2** — TDD, integration. A unit test of any single stage passes while the re-resolve/re-admit/preview/replace pipeline is broken.
- **AC3** — TDD, unit, over each `ref_kind` F1 enumerates.
- **AC4** — TDD, integration. The identity decision is a unit; its observable outcomes are install-route behaviours over a real row and projection.
- **AC5** — TDD, unit. The boundary is request construction, not resolution.
- **AC6** — TDD, integration. The comparison is a unit, but the refusal's effect on the stored row is not.
- **AC7** — TDD, integration. A unit test of the comparison passes while the upgrade still writes, so the refusal is asserted against a real projection.
- **AC8** — TDD, integration. The boundary is the pre-write point, where both the output and the effect of declining are observable.
- **AC9** — TDD, integration. The field contract is a property of a real row round-trip.
- **AC10** — TDD, integration. The boundary is the routing decision, which precedes any canonicalisation, asserted over a mixed state file.
- **AC11** — TDD, integration. Only a real run shows that nothing was written.
- **AC12** — TDD, integration. Deletion is a filesystem outcome, not a state one.
- **AC13** — TDD, integration, at the widest boundary in this spec: a remediation is verified by executing it, so the test drives refusal and recovery as one sequence. Every task owning a refusal carries one such case, since a rule verified against one of its instances is not verified.

## Acceptance Criteria

Each criterion names the fact it derives from. A criterion with no fact is out of scope.

- [ ] **AC1 — `upgrade --skill <name>` selects an installed manifestless row.** *(F4, F5, F7)* The `--pack`/`--all` group is relaxed for a standalone `--skill`. `--agent`, `--hook`, `--seed`, and `--command` keep their existing requirement, and `--pack P --skill S` keeps its shipped meaning of upgrading one primitive inside a catalogue pack, which F4 records; a standalone `--skill` never resolves to that meaning, which is how RFC-0098 D6's rejection of the ambiguous form is satisfied. `--scope` and `--adapter` are accepted and are how a name matching rows at more than one scope or adapter is disambiguated; neither is defaulted. AC11 governs `--dry-run`. Every refusal that reaches handler code writes nothing and carries a registered `DIRECT_CODES` member; the exit-2 usage errors below are argparse's and carry neither, which is why they are enumerated separately. Exit 2 is reserved for the usage errors decidable before state loads. Two are values F5 measures and this criterion holds: a bare `upgrade` with no selector and `--scope local`. A positional catalogue argument alongside a standalone `--skill` is a third exit-2 case that no fact row baselines, because the combination is new here; AC2 reads no catalogue. Two are changes rather than preservations: `--skill` with `--all`, which F5 measures at 1 with `--skill` silently ignored, becomes a usage error; and `--source` without a standalone `--skill`, which no fact row baselines because the flag is new here, exits 2 rather than being discarded in silence by a catalogue route that reads its target from the resolved `pack.toml`. Every other refusal in this list exits 1, matching the codes F5 measures — for most because they are knowable only after loading state, and for `--format json` because exit 1 preserves the shipped guard's own exit: a name matching no installed row; a name matching rows at more than one scope or adapter, naming the flag needed to disambiguate; a row whose `source-kind` is `pack`, stating the direct-pack route is not built; a row whose `source-kind` is absent, which F3's field list gives as the catalogue-pack default and which this route does not serve; and `--format json`, which this route does not support and whose refusal must not reach the shipped `--pack`-worded guard F5 records once T3 makes it reachable. `--scope local` is the exception that stays at exit 2: F5 measures `cli.py` declaring `choices=("repo","user")`, so it never reaches state, and this spec does not widen that choice set — doing so would move `upgrade --pack P --scope local` off the exit 2 that RFC-0098 D6 calls unchanged and `direct-lifecycle-cli-grammar-stability` owns. RFC-0098 D6 mandates local scope for standalone skill upgrade; not delivering it is a knowing partial delivery recorded in `## Assumptions` and owned by `direct-lifecycle-local-scope`. A successful upgrade exits 0, and so does a run that finds no update available; the latter says so on stdout, so the two outcomes are distinguishable without reading the state file. What a successful run prints beyond that is `direct-lifecycle-receipts`'. That decision is AC6's and sits **after** AC2's re-resolution and preview and **before** AC8's confirmation, so a no-update run never asks the adopter to confirm a no-op.
- [ ] **AC2 — A selected upgrade re-resolves, re-admits, previews, and replaces.** *(F4, F7)* It reads the row's `source` and `source-path`, runs the shared admissibility gate over them — and when the re-resolved revision no longer admits that `source-path`, because the upstream renamed or removed the skill directory, exits 1 with a registered member naming the path it looked for and a remediation satisfying AC13, writing nothing — prints the file plan it would write — enumerating the removals AC12 requires as well as the writes, since a plan that omits the run's one destructive action is not a preview of it — and replaces the projection through the same writer install uses. A destination whose on-disk bytes match neither the incoming content nor a digest the row records is an adopter edit: the upgrade refuses it, writes nothing, and names it. That refusal takes its own `DIRECT_CODES` member rather than reusing install's, because `CAT_D009` already carries two remediations and a third would make the printed advice ambiguous — including when the file is one AC12 would otherwise delete, because a silent delete of adopter-edited bytes is the one outcome this route must not have. No part of the run reads a catalogue.
- [ ] **AC3 — `--source` names the revision for a row whose stored source is a remote ref.** *(F1)* When the row's `ref_kind` is `sha` or `abbreviated-sha`, `upgrade --skill <name> --source <source>` re-resolves the supplied source instead of the recorded one, and exits 1 with a registered member when the supplied source names a different identity than the row's. Only the canonical source element can differ under this flag: `source-kind` and `source-path` come from the row, and F1 records that a source string carries no path component, so the comparison is over the ref-stripped source alone. When the row's stored source is a local path, `--source` exits 1 through a registered `DIRECT_CODES` member, because whether the source is a local path is knowable only after loading state and the parent spec's AC21 reserves exit 2 for usage errors. When the row's `ref_kind` is `ref`, `--source` is **admitted** on the same terms: F1 records that a tag and a branch are indistinguishable in the stored string, so refusing the class would strand every tag-pinned row.
- [ ] **AC4 — Identity is the tuple, and the ref is not part of it.** *(F1, F3, F6, F8)* The collision comparison is `(source-kind, ref-stripped stored source, source-path)`, where the middle element is the stored string with a trailing `@<ref>` removed for a `git+https` source and left whole for a local path. It is **not** `canonicalize_source`'s output, which lowercases scheme and netloc and resolves a schemeless value against the process working directory (F6); reusing that function would satisfy the two cases below by accident. No other normalisation applies: a `.git` suffix and owner/repository case are compared as stored, so two spellings of one upstream repository are two identities. That is deliberate — the parent spec's AC11 case-folds the identity *name*, and widening it to the source string would make a refusal depend on a canonicalisation the stored string never went through. The cost is that respelling a source (`o/r.git` for `o/r`) reads as a second identity and collides, even though `direct_source_acquisition` strips `.git` before building the request and both spellings fetch identical bytes. F8's remove-then-install is that collision's remediation. Two installs whose tuples match are the same identity, and what happens next turns on the stored source string. When it differs — the same upstream at a different ref — install exits 1 with a registered `DIRECT_CODES` member naming `upgrade --skill <name> --source <source>`, the one form AC3 admits for every `ref_kind`, because RFC-0098 D4 states that revision and digest "may change only through upgrade". When it is byte-identical, install keeps its shipped behaviour unchanged: it rewrites the files the row owns and leaves the adopter-edit refusal in place. That is what preserves the repair route for a partially written or drifted projection. It is the remediation AC6 names for every `ref_kind`, because install re-records `source-digest` unconditionally. AC7's remediation is governed by AC13 rather than by row kind. Both refusals fire under `install --dry-run` as well: RFC-0098 D6 requires the dry run to perform the complete preflight, and a preview that prints a clean plan for an install the same command would refuse is worse than no preview. Two installs whose tuples differ, at the same identity name and adapter the parent spec's AC11 supplies to the gate, are a collision `--force` never resolves, including a skill whose `source-path` moved under an unchanged source. That collision raises `CAT-D009`; the different-ref refusal above is the one new member AC4 requires, because it carries a different remediation.
- [ ] **AC5 — A request built from stored provenance is not renormalised.** *(F6, F8)* The stored string is used with no value-changing normalisation between validation and request. A repo-scope in-repository source is stored relative to the repository root, so rebuilding its request re-establishes that root from the state file that owns the row — never the process working directory — and rechecks confinement. A stored source that is absent, sentinel-valued, or fails the parent spec's AC3 grammar exits 1 with a registered member rather than resolving through the default chain, and names a remediation satisfying AC13: such a row's stored source cannot be repaired in place, because every reinstall of a real source lands in AC4's differing-identity branch.
- [ ] **AC6 — An update is decided by digest.** *(F3)* Update availability means the re-resolved envelope's `source-digest` differs from the row's, compared only when the **stored** digest carries a prefix this build knows; the re-resolved side always does, because `direct_source_digest` emits the current prefix unconditionally. A stored digest whose prefix this build cannot compare is never compared, recomputed, or rewritten: the upgrade exits 1 and names a remediation satisfying AC13, as the parent spec's AC13 requires it direct the adopter to reinstallation. Reinstalling re-records `source-digest` from the bytes install wrote, so the unreadable prefix is replaced rather than compared; AC13 is what settles whether a bare reinstall is sufficient for the row at hand. No decision reads `installed_version`, which F3 records is the sentinel on every direct row.
- [ ] **AC7 — A capability that widens refuses; one that narrows proceeds.** *(F1, F2, F8, F9)* Upgrade exits 1 with a registered member, writes nothing, and names a remediation satisfying AC13 that reaches the wanted revision through install, whose declared surface and confirmation the parent spec's AC20 contracts. F1 rules out a bare reinstall for a pinned row, which cannot move it at all; so the adopter accepts the widened surface explicitly rather than through a quieter prompt. This refusal is decided before AC8's confirmation, so a refused upgrade never prompts. When more than one refusal in this spec applies to a run, every applicable one is reported and the run exits on the first that is decidable, in the order the run reaches them: the remote `--yes` refusal F7 measures firing before acquisition, then AC5's stored source and AC6's uncomparable prefix, both decidable from the row alone, then AC2's adopter edit and this one, which both need the re-resolved bytes. Refusals decidable at the same stage are all reported; the first in that order supplies the remediation AC13 governs. It fires when: `allowed-tools` gains a member **or becomes absent**; `metadata.boundaries` **gains** a constraint, because a boundary names a capability the skill crosses; `metadata.credentialed` moves to any value that is not `"false"` or `"undeclared"`, which the direct route reads unvalidated so the set is open; or the prior surface cannot be read back at all, which is reported as `unknown` and refuses on its own — a state carrying no per-axis difference, so a predicate reading only differences admits the least-safe case. The prior surface is read by re-deriving the three axes from the installed projection's frontmatter, which F9 records as code this spec builds rather than calls — a single bounded-metadata parse, and what the parent spec's AC12 already requires. **That read is integrity-bound to the row.** The projected `SKILL.md` is parsed only after its bytes match the digest the row records for that path — `files[<relpath>]["sha"]`, reached through the shipped `PackState.file_sha` accessor, so no state field is added and schema 0.5 is unchanged. Any mismatch yields `unknown` and refuses, **including bytes that equal the incoming candidate**. Without that binding the projection is an adopter-writable input trusted as security history: writing the incoming revision's `SKILL.md` into the destination before the run passes AC2, whose adopter-edit test admits bytes matching the incoming content, and then leaves this criterion comparing the new surface against itself, seeing no widening, exiting 0, and letting AC9 convert the widened surface into recorded provenance. The digest comparison is the only step that distinguishes "the adopter already had this" from "someone put this here", so it precedes the parse rather than following it. A narrowing on any axis proceeds. No flag admits a refusal while `direct-lifecycle-capability-reconsent` is open.
- [ ] **AC8 — An upgrade consents to no less than an install.** *(F7 for the pre-acquisition ordering; otherwise inherited — parent AC20)* Before replacing, upgrade prints the same publisher-derived summary install prints for the same source, inside the parent spec's AC18 delimiters and under the `admissible—not safe` verdict emitted both before and after the publisher block. It then takes the same affirmative confirmation install takes, naming every element RFC-0098 D5 lists — the source, the selections, the revision and digest, the scope, the adapter, and the destination — and showing the re-resolved revision and digest beside the row's stored pair, which is the one addition upgrade makes to install's surface. A declined confirmation leaves the state file and the projection byte-identical. A remote upgrade requires `--yes` whether or not a terminal is attached, as F7 records, and that refusal happens before acquisition, so it produces no summary and must not claim one — the ordering install already holds, and the reason `--dry-run` is the route to a summary before consenting.
- [ ] **AC9 — A successful upgrade rewrites exactly the row fields the new bytes invalidate.** *(F3)* In one state mutation, through the write path the parent spec's AC12 contracts: `source-revision`, `source-digest`, and `files` are replaced with the values the run resolved, and `source` only when `--source` supplied one. `source-kind`, `source-path`, `scope`, and `adapter` are unchanged, and `installed_version` keeps the manifestless sentinel — writing a real version there breaks the guarantee `list-installed` depends on. `archive_sha256`, `artifact_uri`, `install_route`, `primitives`, `primitive_versions`, `target_file`, `hook_wiring_owned`, and `user_root` are the eight F3 records the direct route never writes; an upgrade leaves every one of them untouched, so an upgraded row carries exactly the fields a fresh install of the same source would. Because `files` is the ownership map, a file the upstream removed is no longer owned and a file it added is. A second `upgrade --skill <name>` immediately after a successful one reports no update available. AC12 governs the files the new revision drops.
- [ ] **AC10 — No catalogue route reaches a direct row.** *(F4, F5, F8)* A bulk `upgrade --all` skips every row whose `source-kind` is `skill` or `pack` before any stored source is canonicalised, and names each skipped row with the single-row command that reaches it — `upgrade --skill <name>` for a `skill` row, and for a `pack` row the statement that no route is built. `upgrade --pack <name>` naming either kind refuses the same way and before any catalogue is resolved: F4 records that the single-row route gates on `state.has_pack` alone, which matches a direct row by name. A skipped row keeps its place in the table and in the `--format json` document's `summary.total`, carrying the skip as its `STATUS`/`OUTCOME` pair and the reaching command as an additive string field, so `schema_version` stays 1. Its version renders as an em dash on both surfaces — the table cell and the JSON value — matching what F5 measures `list-installed --format json` already emitting for a direct row, so no key is removed and `schema_version` stays 1. The parent spec's AC26 first sentence requires that of every surface; F5 records these two as the baseline departing from it. The `--pack` refusal exits 1 and takes its own `DIRECT_CODES` member, distinct from the bulk skip's, because the two carry different remediations. A bulk run whose only non-success is a direct-row skip exits 0. That requires the skipped row to leave the `unknown` status bucket the exit is computed from — F5 measures a direct row arriving as `STATUS = unknown`, which makes every row `blocked` and the run exit 1, so a mixed installation would be red forever. The row is filtered on `source-kind` before status is assigned, and carries a distinct `skipped-direct` status and outcome rather than reusing `skipped`, which already means up-to-date or ahead and whose counter must keep that meaning. Its own `summary.skipped_direct` counter joins the set, and the status counters still sum to `summary.total`; both are additive, so `schema_version` stays 1. The parent spec's AC22 fixes a direct row's `STATUS` to `unknown` in `list-installed`, which this does not touch — `upgrade`'s bulk table is a different surface, and the parent's clause is `direct-lifecycle-display`'s. Every command this criterion prints is shell-quoted per the parent spec's AC11 and satisfies AC13, which owns the flag set — including the `--root` a bulk run resolved, whose omission F8 measures as fatal from any other directory. AC5 and AC7 therefore govern the single-row direct route only. The skip is this spec's terminal answer, not an interim one: bulk direct upgrade is `direct-lifecycle-capability-reconsent`'s, which owns the all-or-nothing re-consent that makes a bulk run over direct rows safe.
- [ ] **AC11 — `--dry-run` performs the route and writes nothing.** *(F7)* It re-resolves, re-admits, and prints the plan AC2 contracts, then stops, leaving the state file and the projection byte-identical. It performs every refusal the wet run performs — AC2's adopter-edit refusal, AC6's no-update and uncomparable-prefix outcomes, and AC7's widening refusal — and reports them instead of a plan, on the same ground AC4 gives for `install --dry-run`: a preview that omits a refusal the same command would raise is not a preview of it. A dry run that reports a refusal exits with that refusal's exit; a clean preview exits 0, which is what the shipped flag documents. It is exempt only from AC8's confirmation and from the remote `--yes` refusal, on the grounds RFC-0098 D5 states — a dry run never prompts or writes, and is the only way to read the admissibility summary for a remote source before consenting.
- [ ] **AC12 — A file the new revision drops leaves the projection.** *(F3, F8)* A file the row owns that the re-resolved envelope does not contain is deleted from disk in the same run that rewrites the row, unless AC2 refuses it as an adopter edit, in which case the run writes and deletes nothing. A file another row still owns is kept, not deleted. F3 measures that shape as reachable across scopes anchored to one root, because the foreign-owner guard resolves a single state file and cannot see the other scope's rows; `uninstall` resolves it the same way. A directory the deletion empties is pruned. F8 measures why: the install route has no deletion pass, so such a file survives both a reinstall and a subsequent `uninstall`, stranding publisher instruction bytes that no row owns and no command reaches. The deletion runs **before** the state write in the same run. An interruption between them then leaves a row owning a file that is already gone, which is self-healing: `uninstall` treats an absent owned file as already removed, drift counting skips it, and the next upgrade rewrites `files`. The reverse order would leave the residual F8 measures as reachable by no command, which is the worse of the two failures. AC28's surfacing clause is scoped to the interrupted-install case and does not reach a residual left by a completed run; F8 measures that neither `install`, `list-installed`, nor `--check-drift` surfaces one. **Both incomplete outcomes are contracted, because the success path alone lets a fail-open handler pass every other assertion here.** An ownership determination that cannot complete — the cross-scope peer state file being unreadable, which F3 measures as the reachable shape — **keeps the file _and_ keeps its `files` entry**, matching the parent spec's AC28 precedent that a sweep whose protected set cannot be built refuses rather than proceeding on an empty one. Keeping the bytes without keeping the ownership is the failure mode, not the fix: AC9 otherwise requires that a file the upstream removed is no longer owned, so this is a named carve-out from that clause. Without it an implementation reusing the shipped writer, which builds `files` from what it wrote, keeps the file, drops the path, and produces F8's residual exactly whenever the unreadable peer does not in fact own it. This branch takes no refusal and no `DIRECT_CODES` member; the run proceeds. A failed `unlink` or prune is different: it **ends the run under a registered `DIRECT_CODES` member and writes no state row that disowns a file still present**, because the alternative is F8's residual reached the other way — a `files` map that no longer owns bytes still on disk, which no command reaches.
- [ ] **AC13 — A printed remediation terminates.** *(F7, F8)* This criterion governs every refusal that **prints a next command**: AC2's two, AC4's different-ref refusal, AC5, AC6, AC7, and AC10's `--pack` refusal. A refusal that states a route is not built — AC1's `pack`-kind and absent-kind cases, AC10's bulk `pack` skip — prints no command and is outside it, as are the exit-2 usage errors AC1 preserves, which carry argparse's own message and no `DIRECT_CODES` member. Each governed refusal declares its class in this spec, not at emit time. The printed sequence is the diagnostic's `remediation` field, shell-quoted per the parent spec's AC11 — **not** inside the AC18 publisher-data delimiters, which fence untrusted publisher bytes and must not be diluted by agentbundle's own instructions. It carries every flag the refused invocation resolved — including `--root`, which F8 measures as fatal to omit. The rule is that executing it, from the working directory in which the refused command ran, reaches the terminal state its class names, and each refusal declares its class:
  - **Self-contained** — the sequence is fully derivable from the row and the invocation, and reaches an installed row at the wanted revision. AC4's different-ref refusal, AC6, and AC7 are this class. A remote `install` in such a sequence carries `--yes`, because F7 measures the remote gate firing regardless of a terminal; that is exactly the consent install always takes, and the parent spec's AC20 keeps the declared surface printed, so the sequence consents no less than an install and no less than AC8 requires.
  - **Adopter-supplied** — the sequence needs a value the run does not hold, such as AC5's real source or the new path when AC2's re-resolution no longer admits `source-path`. The refusal prints the sequence with that value as a single named placeholder and nothing else left open. Its terminal state is an installed row at the source the adopter supplied, with no unowned publisher bytes left behind, and the rule is verified against the filled form using a fixture value.
  - **Removal-terminal** — no installed row is reachable and the adopter is directed to remove. AC2's `source-path`-no-longer-admitted refusal is this class when the skill is gone from the upstream rather than moved: the terminal state is a removed row with no unowned publisher bytes.

  A projected file the adopter has edited is never destroyed to satisfy this criterion: F8 measures `uninstall` keeping such a file and the following install refusing it, so a sequence that would otherwise strand the adopter names the edited path and the choice to move or keep it as an adopter-supplied step. Where a sequence terminates in another of this spec's refusals — AC4 naming an upgrade that AC7 then refuses — the second refusal is itself a contracted outcome and satisfies this criterion.
