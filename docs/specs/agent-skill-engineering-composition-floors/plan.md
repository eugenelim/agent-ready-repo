## Approach

The slice builds the mechanism before its content, because the mechanism is what
slice 3b inherits and the content is what proves the mechanism can fail. The
lifecycle-state function and the roll-up are pure over `(rows, reference_date)`,
so they land first and are driven by synthetic dates; the Claude Code profile
then supplies the only rows in the repository that can reach `verified` through a
probe rather than a citation. The three composition floors are independent of
both and land in parallel.

The riskiest part is not the schema — it is the re-measurement. Admitting four
topics moves four binding digests on two recorded runs, so 61 existing retrieval
cases, roughly 8 new ones, and the fixed 40-case negative set all have to be
re-observed in independent read-only subcontexts. That work is mechanically
uniform and is the one task that carries a reproducibility obligation rather than
a decomposition.

**Review shape: MIXED**, decomposed into the five dependency-ordered layers the
task DAG produces. Each layer leaves the repository working: after the mechanism
layer the ledger is exercised by its own tests with no content; after the content
layer the topics are admitted and measured; after the surfaces layer the shipped
statements agree with what shipped.

## Design (LLD)

### Design decisions

The ledger is one fixture keyed by runtime, not one fixture per runtime, so slice
3b appends rows rather than adding files and the completeness test reads a single
population. The roll-up is stored *and* recomputed: storing it makes the intended
value reviewable in the diff, recomputing it makes a hand-edit fail.

### Data & schema

`tests/fixtures/runtime-capability-ledger.json` carries `schema_version`, an
`evaluated_at` date, and a `profiles` list. Each profile carries its `runtime`
identifier matching the provider contract's `identifier_pattern`, the `topic`
slug it projects into, `declared_window_days`, its stored `roll_up`, and a
`capabilities` list. Each capability carries `capability`, `state`, `scope`,
`surface`, `os`, `last_verified`, `revalidation_trigger`, a `sources` list whose
members each carry a title, an absolute URL, a `retrieved_at` date and the
source's exposed version or `none exposed`, and
an optional `probe` record carrying its gesture, its observed outcome, and
whether that outcome passed — a probe that ran and failed is neither absent nor
passing, and without the recorded result it would take the probe-present branch
and compute `verified`. The
required-capability set per runtime is declared separately, and carries a
`source_ref` naming RFC-0097 D3 plus an `expected_count`, so that "required row
absent" is detectable and so that deleting a capability from both the rows and
the required set fails.

The absence register's expected count lives in a new
`tests/fixtures/` transcription of the register, mirroring `topology-leaves.json`.
It does not go in the register's own frontmatter, which is asserted equal to a
closed five-key dict at
`packs/agent-skill-engineering/tests/pack/test_foundation_corpus.py:141-147`, and
it does not go in shipped content.

`state` is stored on the row *and* recomputed, for the same reason the roll-up
is: storing makes the intended value reviewable in the diff, recomputing makes a
hand-edit fail. Without the row-level comparison the roll-up's own check is
built on values nothing verifies.

### Interfaces & contracts

No provider seam changes. RFC-0097 D3 requires the router to return each selected
claim's state and the profile roll-up, and the shipped response cannot carry
either: it is a closed field set whose `profile_provenance` entries are validated
against exactly `{profile, retrieved_at, verified_at}`, and a non-`ok` status is
refused if it carries any payload at all. Two further facts make a 3a attempt
worse than useless — the oracle returns an eligible provider's declared status
verbatim, so a case asserting the status it declares proves nothing, and
`ProviderResult` never surfaces `warnings` or `profile_provenance`, so those are
assertable only against the fixture's own declaration. The contract change is
therefore designed once in 3b against eight profiles.

One shipped guard must widen: `single-ecosystem-contract` is today asserted to
apply only to language-specific topics
(`packs/agent-skill-engineering/tests/pack/test_corpus_admission.py:140-144`).
Admitting a runtime-profile topic under that class requires admitting
runtime-profile topics there, which D8 authorizes by name at
`docs/rfc/0097-agent-skill-engineering.md:503`.

### State & control flow

`resolve_state(row, reference_date, window_days)` returns one of the four states.
`unavailable` is a recorded property of the row and short-circuits. Otherwise
window elapse is computed from the maximum `retrieved_at` across the row's
sources — the date the authority makes `verified` depend on, and the one an
author cannot advance without a fresh retrieval; an elapsed window returns
`stale` regardless of probe. Inside the window, a probe record reporting a pass
returns `verified`, a probe record reporting a failure returns `experimental`,
and an absent probe record also returns `experimental`. Every co-occurrence is
decided by the first matching guard in that chain, so no pair needs its own
rule.

### Failure, edge cases & resilience

A `last_verified` later than the maximum `retrieved_at` across the row's
sources — a verification date advanced without a fresh retrieval — is rejected.
A malformed or absent date, a window exceeding 90 days, an empty sources list, a
source whose URL is relative or repository-internal, and a probe record without an
observed outcome are each rejected with a named diagnostic rather than defaulted
into a state.

### Dependencies & integration

No new runtime dependency. The state function uses `datetime.date` from the
standard library.

### T2: The lifecycle states and roll-up are computed and each can fail

**Depends on:** none

**Verification mode:** TDD. Implements AC9, AC10, AC12, AC14, AC15.

**Tests:**
- Four inputs, one per state, each named in the test rather than asserted as a
  set membership.
- The co-occurrence case — a row both absent and past its window — pinned to the
  stated resolution order, so evaluation order cannot decide it silently.
- Advance only the reference date past the declared window: `verified` becomes
  `stale`. This is the killing mutation for window elapse.
- Strip the probe record from a `verified` row: it becomes `experimental`.
- Flip a probe record's result to failed: the row becomes `experimental`, not
  `verified`. Without a recorded result this case is indistinguishable from a
  pass, which is why the schema carries one.
- Edit a row's stored `state` away from its computed value: fails.
- Edit a profile's stored `roll_up` away from its recomputed value: fails. Drive
  both from a fixture copy, never by editing the shipped ledger.
- Remove a required row: `incomplete`. Set a required row `unavailable`:
  `complete-current` still holds.
- Each rejection case in *Failure, edge cases & resilience* raises its named
  diagnostic; a window declared above 90 is one of them.

**Approach:**
- Pure functions over supplied values; no test reads the wall clock.
- Give the required-capability set a class-isolating control per member, so one
  member's absence cannot be satisfied by another's — the shadowing defect
  recorded at `packs/agent-skill-engineering/tests/pack/test_corpus_admission.py:840-845`.

**Done when:** every mutation above reddens the test named beside it.

## Rollout

No migration and no runtime flag. The pack's installed behavior changes only by
gaining topics; no provider field or status changes meaning here.
Installers see the change through the version bump.

## Risks

- **The re-measurement is the schedule risk.** Roughly 110 independent
  observations across two records; a host interruption mid-run produces a partial
  record that is not a measurement. Discard and re-take rather than recording
  partial, and write each run to a unique path.
- **A probe that proves the harness, not the runtime.** A capability "verified" by
  observing this session's own tooling rather than the documented contract would
  ship a false `verified`. Each probe records the gesture and the observed outcome
  so a reviewer can judge whether the gesture tests the claim.
- **The ledger's first consumer is also its designer.** Slice 3b is the real test
  of whether the schema fits seven more runtimes. Keeping the required-capability
  set as data rather than as code is what makes a bad guess cheap to correct.
