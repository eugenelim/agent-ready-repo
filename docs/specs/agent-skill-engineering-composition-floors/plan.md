## Approach

The slice builds the mechanism before its content, because the mechanism is what
slice 3b inherits and the content is what proves the mechanism can fail. The
lifecycle-state function and the roll-up are pure over `(rows, reference_date)`,
so they land first and are driven by synthetic dates; the Claude Code profile
then supplies the only rows in the repository that can reach `verified` through a
probe rather than a citation. The three composition floors are independent of
both and land in parallel.

The riskiest part is not the schema — it is the re-measurement. Admitting four
topics moves four binding digests on two recorded runs, so 61 existing retrieval
cases, roughly 8 new ones, and the fixed 40-case negative set all have to be
re-observed in independent read-only subcontexts. That work is mechanically
uniform and is the one task that carries a reproducibility obligation rather than
a decomposition.

**Review shape: MIXED**, decomposed into the five dependency-ordered layers the
task DAG produces. Each layer leaves the repository working: after the mechanism
layer the ledger is exercised by its own tests with no content; after the content
layer the topics are admitted and measured; after the surfaces layer the shipped
statements agree with what shipped.

## Constraints

- The taxonomy stays at 36 leaves. Admission moves leaves between the admitted set
  and the absence register; it never adds one.
- Neither user-facing workflow's `SKILL.md` changes, which is what keeps the
  recorded activation observation and its digest pin in force. Any change there
  forces re-observation of activation before this slice can close.
- Shipped pack content cannot cite repository paths, spec or governance
  identifiers, or `workspace.toml`.
- `make build-self` refuses a dirty tree, and the aggregated marketplace manifest
  is regenerated by `catalogue self-host` rather than hand-edited.
- `pytest` and `make build-check` cannot run concurrently: pytest writes
  `packs/**/__pycache__` that build-check rejects.

## Design (LLD)

### Design decisions

The ledger is one fixture keyed by runtime, not one fixture per runtime, so slice
3b appends rows rather than adding files and the completeness test reads a single
population. The roll-up is stored *and* recomputed: storing it makes the intended
value reviewable in the diff, recomputing it makes a hand-edit fail.

### Data & schema

`tests/fixtures/runtime-capability-ledger.json` carries `schema_version`, an
`evaluated_at` date, and a `profiles` list. Each profile carries its `runtime`
identifier matching the provider contract's `identifier_pattern`, the `topic`
slug it projects into, `declared_window_days`, its stored `roll_up`, and a
`capabilities` list. Each capability carries `capability`, `state`, `scope`,
`last_verified`, `revalidation_trigger`, a `sources` list, and an optional
`probe` record. The required-capability set per runtime is declared separately so
that "required row absent" is detectable rather than inferred from the rows that
happen to be present.

### Interfaces & contracts

No provider contract field is added. `runtime`, `profile_provenance`, and
`stale-profile` are already declared and currently unreachable; this slice makes
each reachable and each falsifiable.

### State & control flow

`resolve_state(row, reference_date, window_days)` returns one of the four states.
`unavailable` is a recorded property of the row and short-circuits. Otherwise
window elapse is computed from `last_verified`; an elapsed window returns `stale`
regardless of probe. Inside the window, a passing probe record returns `verified`
and its absence returns `experimental`.

### Failure, edge cases & resilience

A malformed or absent date, a window exceeding 90 days, an empty sources list, a
source whose URL is relative or repository-internal, and a probe record without an
observed outcome are each rejected with a named diagnostic rather than defaulted
into a state.

### Dependencies & integration

No new runtime dependency. The state function uses `datetime.date` from the
standard library.

### T2: The lifecycle states and roll-up are computed and each can fail

**Depends on:** none

**Verification mode:** TDD.

**Tests:**
- Each of the four states is produced by a distinct input, and the test names the
  input rather than asserting the state set is non-empty.
- Holding a row fixed and advancing only `reference_date` past the window flips
  `verified` to `stale` — the mutation that proves window elapse is computed.
- A stored roll-up that disagrees with the recomputed value fails; this is the
  killing mutation for AC7 and is exercised by editing the stored value in a
  fixture copy, not by trusting the shipped one.
- A required row removed from a complete profile yields `incomplete`; a row set
  `unavailable` leaves `complete-current` standing.
- Each rejection case in *Failure, edge cases & resilience* raises its named
  diagnostic.

**Approach:**
- Write the state function and roll-up as pure functions over supplied values so
  no test reads the wall clock.
- Declare the required-capability set per runtime as data, and give it a control
  that resolves each member by name so one member's absence cannot be satisfied by
  another's — the shadowing defect recorded in the languages slice's `qa.md`.

**Done when:** the new module's tests pass, and each listed mutation reddens the
test named beside it.

## Rollout

No migration and no runtime flag. The pack's installed behavior changes only by
gaining topics and by making three already-declared provider fields reachable.
Installers see the change through the version bump.

## Risks

- **The re-measurement is the schedule risk.** Roughly 110 independent
  observations across two records; a host interruption mid-run produces a partial
  record that is not a measurement. Discard and re-take rather than recording
  partial, and write each run to a unique path.
- **A probe that proves the harness, not the runtime.** A capability "verified" by
  observing this session's own tooling rather than the documented contract would
  ship a false `verified`. Each probe records the gesture and the observed outcome
  so a reviewer can judge whether the gesture tests the claim.
- **The ledger's first consumer is also its designer.** Slice 3b is the real test
  of whether the schema fits seven more runtimes. Keeping the required-capability
  set as data rather than as code is what makes a bad guess cheap to correct.
