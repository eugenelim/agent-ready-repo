> change needs an **amendment** only when it touches the spec's protected
> sections (contract, scope and non-goals, durable outputs, agent rules, testing
> strategy, acceptance criteria, accepted risk) or its `Terminal Intent`. A change
> to tasks, tests, stubs, design, or approach needs none: the controller makes it

> the run continues with every finished task still finished. Execution

> controlled-amendment path.

> **Not every field is contract.** `Touches`, `Tests` and `Done when` are what a
> completion gate reads. `Design`, `Approach`, `Grounding` and `Risks` are working
> material the controller corrects in place, before or after approval, while no
> attempt is open.

## Approach

One roster module, `tests/roster/test_registry_upgrade_notes.py`, carries the operative-set scan (AC-0008, AC-0009, AC-0010, AC-0011, AC-0019). It starts with an empty list of checked surface groups, and each text task adds its own, so every task ends green and the whole set is checked by the last text task. Each task that edits or deletes a file also runs the shipped tests that read that file, and moves their pins in the same task (AC-0020). The riskiest parts are the rename's absence handling (a fail-closed transaction with recovery), the next-action strings (pinned in several copies and the dispatch fixtures), and the twelve roster modules that read the deleted schema page. The upgrade page needs the owner's wording approval mid-run, so it is its own task.

## Design (LLD)

### Design decisions

- **Publish a copy, keep the draft.** The draft's SHA-256 is pinned by a Shipped spec's roster; the page is a new file and the draft's inventory row becomes `historical`. Owner decision, 2026-11-03.
- **Delete two pages, rewrite three.** `migrate-capture-work.md` (rollback only) and `workspace-toml-schema.md` (the registry's schema) are deleted; their inbound links go to the upgrade page. `orient-at-session-start`, `two-room-model` and `your-first-workspace` are rewritten around dispatch. Owner decision, 2026-11-03.
- **Replacement routing, used in every rewrite.** What is ready, active or blocked: `work-loop`'s `dispatch.py`. Captured items: `dispatch.py --captured`. Work placed under an intent: `navigate-intents` `outstanding`. New work: `work-intake`. Lifecycle: the artifact's `Status:`; dependencies: `Depends on:`; tracker profile: the `source-authority` record; refresh policy: `.work-intake.toml`. `workspace-status`: only `repair-plan` and `repair-apply`.
- **Upgrade page outline.** Before you upgrade (finish or roll back a recorded `.workspace-migrations.json` operation on the old version); upgrade; plan the repair; apply it (the four drop steps, `needs-to-header`, `captured-entry-drop`, `refresh-policy-move`); what stays in `workspace.toml` (keep the file; initiative tables are not entries); legacy-form entries (hand edit; dispatch refuses with `unmigrated_workspace` until then); retired subcommands and their replacements; MCP `workspace_status()` changes; what is not carried over. The PCC-ADV-05 repair: the "what stays" paragraph names only what remains after the drops, not what the repair removes.
- **Next-action wording.** "…, then run `dispatch.py` again." replaces "…, then rerun reconciliation." in the dispatch-family tables (`work-loop`, `navigate-intents`' copy, the `_data/` copy, `workspace_mcp.py:1058`), and "…, then run `repair-plan` again." in `workspace-status` (`workspace_status_engine.py`, `workspace_status.py:373`, SKILL.md). Whether a parity test compares the `work-loop` table with the engine's text is `implementation-discovered`: if one does, it compares them apart from the next action.
- **Self-host exclusion goes with the seed.** With no seed, nothing projects onto the root `workspace.toml`; self-host prints one non-failing `[info] unclassified: workspace.toml` line until 9G deletes the file. `test_workspace_toml_curated_content_preserved_on_reprojection` pinned the exclusion and is removed; the `"workspace.toml"` literal leaves the expected-pattern list in `test_self_host_check.py`.
- **Rename absence is the `none` mode.** The rename already has a `none` mode: the registry names neither path and the rename never writes it.
  - At a commit, `_registry_mode` decides absence only from a successful `git ls-tree <commit> -- workspace.toml` that lists nothing, and then returns `none`. A listed entry that is not a regular blob (mode `100644`/`100755`), or any Git failure, refuses. `git cat-file -e` is not used: it exits 128 both for a missing path and a bad object, and `_git` discards stderr.
  - In the working tree, absence is an `lstat` `FileNotFoundError` on `<root>/workspace.toml`; `Path.exists` is not used, so a dangling link is present. A present entry that is a link, not regular, unreadable or invalid TOML keeps today's refusals.
  - In `none` mode a live read of an absent file counts as bytes naming neither path. When a live file exists, the `none`-mode citation check at `intent_rename.py:2318-2328` still runs: the citing sweep skips `WORKSPACE_FILE` (`:791`, `:813`), so it is the only guard on the live registry.
  - The request skips its registry step (step 5) only when the file is absent from the working tree. Both dirty checks (`_is_dirty`, `_replacement_targets_are_dirty`) leave `workspace.toml` out of the guarded paths only when it is absent from both the reference commit and the working tree; a one-sided registry stays dirty.
  - Recovery recomputes the mode through the same function. At `:1219` and `:2412` it reads the stage's recorded `base_commit`, which `_derive` requires to equal HEAD (`base-changed` at `:893` otherwise), so it reaches the forward run's answer. Terminal cleanup (`_resume_terminal_cleanup`, `:2434`, `:2478`) only meets stages with no readable base: an empty stage, a marker-only or torn-marker stage, or a torn record naming no request (`:2444-2455`); a record or canonical marker whose base differs from HEAD does not match and is skipped. It reads the mode at HEAD. When the registry is absent there, the mode is `none`, as in the tracked twin whose registry names neither path, so `_validate_terminal_bytes` returns at `:2141-2142` and disposal removes only stage metadata (`:2512-2535`). No registry step can be pending: empty and torn-marker stages are past terminal validation, and a torn record is before any live write. Refusing instead would strand every such stage in a repository without `workspace.toml`.
  - The working-tree absence test also requires a successful `git ls-files -- workspace.toml` that lists nothing, so a registry held only in the index stays in both dirty checks' guarded paths. Any failure or timeout of that query counts as present, in both modules (the request module's own `subprocess.run` calls check the exit status).
  - In `none` mode the rename never writes, links through or temp-stages `workspace.toml`, so a registry created after the pre-write check cannot redirect a write; it sits outside the rename's guarantee, as the existing comment at `:2317-2318` records.
  - A base run in a repository with no `workspace.toml` refuses `registry-unparseable` at the request step.
  - AC-0018 compares status, refusal code and, for the request, the resolved fields other than `repository_root`; `operation_id` is random (`secrets.token_hex(16)`) and is not compared.
- **Roster scan shape.** Surface groups are glob lists keyed by task. A Markdown mention unit is a table row, a list item with its indented continuation lines, a paragraph, or one line of a fenced block (Mermaid included) or of frontmatter; headings are skipped. JSON strings are walked recursively. Word matching follows the spec's Word match term.
- **Journey pages.** T5 and T6 edit `packs/*/JOURNEY.md`; T6 then runs `tools/build-site.py --journeys-only` and commits `web/src/content/journeys/`.

Owned by: T1 (scan), T2 (page), T3 (seed), T4 (next actions), T5 to T9 (text), T11 (rename).
