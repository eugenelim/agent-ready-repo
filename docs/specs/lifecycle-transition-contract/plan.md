# Plan: An intent's lifecycle state is a closed contract a lint can decide

- **Spec:** [`spec.md`](spec.md)
- **Status:** Done <!-- Drafting | Approved | Executing | Done -->
- **Repository anchors:** `packs/core/AGENTS.md` (pack export boundary, test loader rule, version bump rule); `docs/AGENTS.md`; [ADR-0119](../../adr/0119-retire-the-initiative-ladder-into-the-recursive-intent-graph.md); [ADR-0121](../../adr/0121-a-repository-intent-declares-its-altitude.md) D1

## Approach

One lint gains one refusal class. The state-coherence rules are pure predicates over a preamble the module already parses, so the work is additive inside an existing parse and needs no new module, script, or dependency.

The migration runs first, and the rules land on a corpus that already conforms. `intent-preamble-lifecycle-records` shipped both records' value shape on 2026-09-23, so `_check_dated_evidence` validates each record as it is written — which is the as-it-lands check the original ordering put T1 and T2 ahead of the migration to supply. Running the migration first satisfies the parent's "the rule may not ship before it runs" more strictly than the original order did, because the rule never exists against a corpus it would refuse. The migration is a per-artifact judgement for each intent the rules will refuse, not a sweep.

## Constraints

- `.apm/` is the runtime export boundary. Tests never live there, and every `.apm/` edit reprojects through `make build-self`.
- A non-cosmetic pack-content change bumps matching versions in `pack.toml` and `.claude-plugin/plugin.json`.
- The lint runs in `.github/workflows/docs.yml` against the real tree, and `tools/test_intent_corpus_gate.py` asserts a job invokes it. Both surfaces pin the invocation; neither may drift.
- `tests/roster/test_intent_template_shape_conformance.py` validates the `frame-intent` template against the corpus-scoped rules as well as the per-artifact ones, so it is a surface this spec must extend, not only a suite that must keep passing. It is the guard that stops a template seeding a shape the lint refuses at the next admission.
- Load the module under a name including its pack and skill. Several skills ship same-named scripts, and a bare import binds whichever directory reached the path first.

## Construction tests

Every state-coherence rule in T2 is a fixture pair — one intent that conforms, one that does not — driven through the module's existing parse rather than a spawned interpreter. Those pairs and T1's registry assertion live in `packs/core/tests/skills/work-intake/test_intent_corpus_lint.py`.

AC-0010 is the exception and is not a fixture pair. It is a differential that reuses those same fixtures, asserting each one's verdict on **both** surfaces, so its home is `test_intent_shape.py`, where the existing seam controls already sit and where `validate_live_intent()` is addressed directly.

The migration's oracle is the real-tree run, not a fixture: `--dir docs/product/intents --root .` exits 0. It is verified at T4, because the refusals it exercises are T1's and T2's and the run cannot discriminate before they exist. T3 runs first and therefore carries a **pre-rule check** as well — an inline derivation over the same real corpus, listed in its `Tests:`. That is not a fixture and does not stand in for the oracle: it reads the live tree, and AC-0014's lint run still has to pass at T4 on the corpus T3 leaves behind.

## Design (LLD)

### Design decisions

- **The rule is decidable from one snapshot, which is why it is expressible at all.** A transition is a pair of states and the lint sees one, so the contract is a coherence rule between a state and the records beside it. `Fulfilled` is not "reached `Accepted` at some point"; it is "carries the `Accepted:` record". Ratification has to persist on the artifact for the snapshot to decide it, and that is the whole mechanism.
- **The corpus-lint-only surface becomes one entry point, not two.** A third consumer already enumerates both by name: `tests/roster/test_intent_template_shape_conformance.py` validates the resolved `frame-intent` template through `validate_live_intent()` *and* `validate_supersession()`, and says why — a template seeding a corpus-scoped violation would pass the first check and still be refused at the next admission. Adding a second corpus-only function beside `validate_supersession()` would leave that guard exercising neither of the surfaces carrying AC-0001 to AC-0009, reintroducing the exact failure the file exists to prevent. So T2 adds `validate_corpus_scoped(text, live)` as the single corpus-only entry point, delegating to `validate_supersession()` and to the new state-coherence function, and the corpus lint and the roster suite both call it. One name to enumerate, so the next rule added here reaches every consumer without any of them changing.

  **The residual is reduced, not removed, and this slice does not remove it.** `validate_supersession()` stays public, and it is the name the roster suite reaches for today, so a future consumer can still call it alone and get partial corpus-scoped coverage. Making that unreachable means privatising it, which renames a symbol the corpus lint, the roster suite and a large shipped block of `test_intent_shape.py` all call — more churn than this slice carries, and none of it in service of an acceptance criterion. What T2 does add is a delegation check, so a rule set the aggregator stops reaching reds even though a consumer calling the partial name still would not. § Follow-ons carries the privatisation.
- **The rules are corpus-lint-only, mirroring `validate_supersession()`.** `intent_shape.py` is the single home both enforcement points read, and `validate_live_intent()` is the surface they share. `validate_supersession()` is defined in that module and is not reachable from `validate_live_intent()` — the corpus lint calls it directly — so the seam already exists and the new rules take it. The ground is the dichotomy stated two bullets below: these rules decide one field from a *different* field's value, which is the corpus-lint-only side. What the shaping reviewer's own conditions reach is not the ground and is not asserted; `spec.md` § Follow-ons records it as unsettled.
- **Value shape is not decided here.** Neither `_is_iso_date` (whole-string anchored) nor `_check_date_or_no` (accepts the bare `no`) fits these records, but choosing what does is an intent preamble field's shape and therefore `FEAT-0001`'s. This slice checks presence by state and consumes whatever shape that brief lands.
- **The parser already exposes the records, which is what makes this additive.** `read_preamble()` returns every preamble pair rather than a fixed list. Probed 2026-09-23: adding an `Accepted:` record to a real intent exits 0, and so does an invented `Sprocket:` field — only `RETIRED_FIELDS` are refused. Both records can therefore land on artifacts before the rules ship, which is what lets T3 migrate and be checked as it goes.
- **The refusal classes need a declared registry before a check can read them.** Reasons are constructed inline, so nothing enumerates them today. A module-level tuple of class names, with every new refusal built from a member, is what turns the docstring obligation from a sentence-exists check into a set comparison. Pre-existing classes stay out of scope: retrofitting them is a larger change than this slice carries.
- **Two seams meet at these two fields, and this is the one place the split is decided.** `intent-preamble-lifecycle-records` put the records' *value shape* on the shared surface; this spec puts their *presence by state* on the corpus-lint-only one. Its follow-on asked for the boundary to be stated in one place before a third rule reached either seam, and slice 1 is that third rule. T4 copies the statement below into `intent_shape.py`'s module docstring, which is the living home a future author reads, and reduces the two places that argue the split today — the module docstring's own `validate_supersession` sentence and `_check_supersession_pair`'s docstring — to pointers at it.

  **The rule.** Among the rules deciding a **live intent**, a rule whose verdict depends only on the field it constrains belongs on the shared surface; a rule whose verdict depends on a different field's value, or on another artifact, belongs on the corpus-lint-only surface. "Only the field it constrains" covers that field's presence, its name, how often it occurs, its value, and — where its value gates whether the check runs at all — a fixed location in the same artifact. **Why a cross-field rule stays off the shared surface, given that it needs only one artifact.** Not because the shaping reviewer's condition 7 reaches it — § Follow-ons records that reach as unsettled, and this split deliberately does not rest on it. Because the placement is the one that is safe under either answer. If condition 7 does reach such a rule, putting it on the shared surface changes what the reviewer decides and owes an amendment to a `Shipped` spec; if it does not, the corpus-lint-only placement costs nothing. Shared placement would buy something under reach=yes — the rule would be enforced when an intent is *written*, not only in CI — so the ledger is not one-sided. This spec declines that benefit on grounds it already records rather than on grounds invented here: § Outcome scopes the contract to what "the corpus lint can decide from the artifact alone", and § Follow-ons assigns write-time transition enforcement to `close-work` and slice 2, because preventing an illegal move needs a writer that knows both the current and proposed status — which a reviewer reading one snapshot does not. So the benefit is real, out of this slice's scope, and owned elsewhere; the cost is a shipped spec's enumeration. One option is harmless under both answers and the other is not, so the open question is settled for placement purposes without being settled on its merits. The resolution half needs no such argument: `validate_live_intent()` decides from one artifact and resolution needs the corpus, which `intent_shape.py`'s docstring already records. **What this argument does not do.** It grounds *this spec's* placement, not the dichotomy as a whole. Taken as a free-standing principle it would also move `_check_dated_evidence` off the shared surface — that rule is precisely what raises the reach question — and `intent-preamble-lifecycle-records` is `Shipped` with it in `VALUE_RULES`. This spec does not re-litigate that: where the value rules sit is the sibling's decision, taken deliberately and already delivered, and the dichotomy's shared arm describes where the module's rules sit today rather than re-deriving each one. The argument applies to a rule whose placement is still open, which is what slice 1's rules are and what the sibling's are not. If the reach question later settles as enumerations-only, the pairing half is worth revisiting; § Follow-ons carries that.

  It routes every rule in the module today: required-field absence, duplicate occurrence, retired name and the value rules on the shared side; `_check_direct_light_decomposition` there too, because `Decomposed:`'s terminus only decides *whether* `## Decomposition` is read and the heading is fixed in the module rather than named by the value; supersession's pairing rule on the corpus-lint-only side because it decides one field from another field's value, and its resolution rule because it needs the rest of the corpus. This spec's rules land there for the pairing rule's reason. The tombstone contract in `intent_corpus_lint.py` is a third home and outside this rule, which governs live-intent rules only.

  **Carried as a closeout condition rather than a criterion.** An earlier draft made it AC-0015, asserting the module carries exactly one normative statement of the split. That was dropped: a content pin would catch a copy-pasted restatement and pass a pointer, but nothing catches a paraphrase, so the criterion's stated obligation outran any control available to it. It is not that a criterion must be machine-decidable — `new-spec`'s contract admits a manual-QA criterion and `spec-plan-prose-discipline` ships one — only that this obligation was written to claim more than it could check. It survives as the `## Durable Outputs` *Current architecture* closeout condition, which a human decides and records in `notes/verification-ledger.md` — one row naming the verdict and the date, so the judgement is evidence rather than an assertion that it happened. Where the rules actually sit stays AC-0010's, and that is mechanical.

- **`Withdrawn` is deliberately exempt.** Abandoning an unratified bet needs no ratification, so requiring `Accepted:` there would refuse a legitimate state.

### Data & schema

Two preamble records, whose value shape `intent-preamble-lifecycle-records` fixed and this spec consumes: an ISO 8601 calendar date `YYYY-MM-DD`, a space, then non-empty text carrying the decider and the evidence. The text is **required**, not optional — a bare date is refused, because the record exists to carry the evidence. The bare literal `no` is refused too: unlike the progress fields, these record a fact rather than offer an opt-out.

### Behavior & rules

The spec's criteria own the rule set. This table is the implementation's dispatch shape, not a second statement of the contract:

| `Status` | requires `Accepted:` | `Fulfilled:` |
| --- | --- | --- |
| `Draft` | refused if present | refused if present |
| `Accepted` | not decided here | refused if present |
| `Fulfilled` | required | required |
| `Cancelled` | required | refused if present |
| `Withdrawn` | not required | refused if present |
| `Superseded` | not decided here — see the spec's not-changed paragraph | not decided here |

### Failure, edge cases & resilience

- A record below the preamble reads as absent, so a body-positioned `Accepted:` does not satisfy AC-0001. The existing bounding stage gives this for free; the risk is adding a whole-file scan that bypasses it.
- Exit 2 for an unreadable corpus stays distinct from exit 1 for a non-conforming one.

### T3: Migrate the corpus

**Depends on:** none

**Mode:** Goal-based check

**Approach:** A per-artifact judgement for each intent the rules will refuse, not a sweep. Two sets, both derived from a run: those owing a record, and within them those that never reached `Accepted`, which owe a status judgement. **Owner decision, 2026-09-24 — the walk-backs rest on an owner waiver rather than a shaping review.** The parent's `Draft` → `Accepted` price is an independent intent-mode review plus human confirmation; the owner waived the review half for this one-off migration and confirmed each artifact directly. The waiver is recorded per artifact in `notes/migration-record.md`, which `## Durable Outputs` already admits by requiring "the review **or waiver** it rests on". No `Accepted:` value may describe a review that did not run.

**Tests:**
- A derivation over `docs/product/intents/` returns the empty set of violations, taking one predicate per state directly from the spec's criteria rather than restating them: `Fulfilled` requires both records (AC-0001, AC-0004); `Cancelled` requires `Accepted:` and forbids `Fulfilled:` (AC-0002, AC-0009); `Withdrawn` requires no `Accepted:` and forbids `Fulfilled:` (AC-0003, AC-0009); `Draft` forbids both (AC-0007); `Accepted` forbids `Fulfilled:` (AC-0008). `Accepted`'s own `Accepted:` record is not decided here, per the spec's *Not changed here* paragraph. This is T3's **pre-rule check**, and it is the only check that can fail while T3 runs before T1 and T2. It is an inline derivation over the corpus, not a new script — `## Agent Rules` → *Never do* forbids adding one — and the migration record carries the command and its output. **It reads fields through `intent_shape.read_preamble()`, the corpus lint's own parser**, rather than scanning the file. That is what makes it agree with the lint on placement by construction instead of by assertion: a whole-file scan would accept a body-positioned record the lint treats as absent, which is how 22 misplaced fields landed earlier in this family, and a hand-rolled boundary would only be claimed equivalent. Proven differentially — the same record bytes read as present in the preamble and as absent one line below the first `##` heading. It reports both sets the spec's `## What Changes` names: the artifacts the rules would refuse, and within them the artifacts that never reached `Accepted` in history. The historical half states its own evidence rather than assuming it — a revision carrying no `Status:` field is counted and reported, because "never ratified" and "the parser could not read it" are the same verdict on different grounds. It refuses rather than guessing on every path where it has not actually read the evidence: a git failure, an empty revision list, a present-but-empty field value, an absent `Status:`, and any status outside the criteria's set other than the deliberately deferred `Superseded`. It scans every revision rather than stopping at the first `Accepted`, so the coverage it reports is of the whole history. Measured over all 14 offenders: one, `rendered-page-visual-inspection`, has 3 of 5 revisions predating the `Status:` field; the other thirteen parse at every revision, and none of the strict refusals fires on today's corpus.
- **AC-0014 is verified at T4, not here.** The real-tree lint run cannot serve as T3's oracle under this task order: the refusals AC-0014 exercises are T1's and T2's, so before they exist the run exits 0 on an unmigrated corpus and the criterion holds without the migration having happened. Measured on `6e89061c3` before any artifact was edited: `intent_corpus_lint.py --dir docs/product/intents --root .` reported `clean — 150 entries, 150 live, 0 tombstone, 0 unreadable` and exited 0. T4 re-runs it once the rules exist, which is the first point at which it discriminates.

**Done when:** its `Tests:` pass, both derived counts are reported from the derivation, and `notes/migration-record.md` carries one entry per artifact in the second set naming the branch taken and the review or waiver it rests on. **This was met on 2026-09-24 in commit `d00f39e34`** — 14 refused and 10 never `Accepted` before the migration, 0 and 0 after, with the migration record written.
